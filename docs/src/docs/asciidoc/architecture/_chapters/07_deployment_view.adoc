== Deployment View

The project has no runtime infrastructure of its own: the processor runs inside the compiler of the user's build. What
is deployed are the build artifacts and this documentation.

Motivation::

Users take the artifacts from Maven Central, and readers take the documentation from GitHub Pages. Both are produced
by automated builds, so no manual upload step exists.

Quality and/or Performance Features::

Every published jar is signed and comes with a sources jar and a Javadoc jar, which Maven Central requires. A
CycloneDX software bill of materials is attached to every published module, so users can see which dependencies it
brings along. Every published jar declares an `Automatic-Module-Name`.

Mapping of Building Blocks to Infrastructure::

[options="header",cols="2,4"]
|===
| Building block | Deployed to

| `matcher-generator-annotations`, `matcher-generator-core`, `hamcrest-matcher-generator`, `assertj-assertion-generator`,
`hamcrest-matcher-generator-kotlin` and the two bridge jars
| Maven Central through the Central Portal.

| `*-endtoend-*` modules, the `example-maven-*` modules, `docs`
| Not published. The release bundle excludes them (`excludeArtifacts` of the root pom). The Gradle example is not a
reactor module and is not published either.

| Documentation
| GitHub Pages, deployed by the `Docs` GitHub Actions workflow after the docs build and its link checks passed.
|===

=== Infrastructure Level 2

==== Release to Maven Central

The `release` Maven profile signs the jars with GPG, attaches the sources jar, the Javadoc jar and the CycloneDX SBOM,
and lets the `central-publishing-maven-plugin` upload one bundle to the Central Portal. The plugin publishes the
bundle automatically and waits until it is published. The former OSSRH is not used any more.

==== Documentation on GitHub Pages

The `Docs` workflow builds the `docs` module on JDK 21, uploads the rendered HTML as a Pages artifact and deploys it
with the official Pages actions. It runs for version tags and on manual request.

The site is published on its custom domain, the one base URL of the docs build (`docs.base.url` in `docs/pom.xml`).
Every page carries a canonical link to its address there. The site root also holds `sitemap.xml` (every rendered page),
`robots.txt` (every crawler allowed, names the sitemap) and `llms.txt`. The `github.io` address of the project only
redirects to the base URL.

[[deployment-required-checks]]
=== Required Checks

The `main` ruleset requires `Build`, `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25`, `Verify JDK latest`, `Domain docs in sync`, `Release dry run`, `Sonar`, `Mutation testing` and `Example Gradle` before GitHub merges a pull request. `Dependency review`, `Scorecard`, `SCANOSS`, `External links` and `PR title` are not required. Scorecard reports only; its score does not gate merges. The jobs are described in <<concepts-ci-gates,chapter 8>>.

[[deployment-release-pipeline]]
=== Release Pipeline

Releases run on CI and need no machine of the owner.

* The squash-merged pull request title must follow Conventional Commits, because it is the commit that release-please reads (the `PR title` job is in <<concepts-ci-gates,chapter 8>>).
* `.github/workflows/release.yml` runs on every push to `main`.
** release-please (type `simple`, default bump rules, configured in `release-please-config.json` and `.release-please-manifest.json`) keeps a Release PR up to date. It uses an App token, so that the PR runs its checks and the new tag triggers the docs deployment.
** Tags have no `v` prefix (`6.0.0`), matching the `[0-9]*` trigger of `docs.yml`.
* The project version lives in the module poms (own and parent `<version>`) and in the Gradle example (marker `x-release-please-version`). release-please raises them through one xml entry per pom in `extra-files`; the README's `x-release-please-version` lines are raised through the `README.md` entry of `extra-files`.
* The `simple` type is used instead of `maven` because the Maven updater rewrites the `@project.version@` of the frozen 5.x suite and misses the parent versions.
* The `simple` type's optional `version.txt` is not created: its updater has `createIfMissing: false`. The release-please 17.11.2 simulation of the 6.0.0 release changed only `CHANGELOG.md`, the Gradle example and the 20 poms.
* Dependencies on project artifacts use `${project.version}`. The 5.x suite and its runner's consumer poms are filtered by the build (`@project.version@`). `scripts/ci/check-project-version.py` guards all of it.
* Merging the Release PR creates the tag and the release page. The same workflow then runs:
** `Release build`: `mvnw -T 1 verify` on the tag;
** `Publish to Maven Central`, only if `Release build` is green: `mvnw -T 1 -P release -DskipEndtoend -DskipTests -DskipITs deploy` (GPG signatures, SBOM, `central-publishing-maven-plugin` waiting for `published`), a build-provenance attestation (`actions/attest`), and it makes sure the release page exists.
* After a confirmed publish, the job `Announce release` comments on the merged Release PR with the App token. The comment mentions the owner and links Maven Central, the release page and the CHANGELOG section.
* A failed publish is re-run with `workflow_dispatch` and the existing tag as input; tags are never moved.
* 6.0.0 is forced with `release-as` and merged by the owner. Auto-merge of Release PRs stays off until after 6.0.0.

[[deployment-credentials]]
=== Credentials

The credentials live in the repository environment `release` (`CENTRAL_USERNAME`, `CENTRAL_PASSWORD`, `MAVEN_GPG_KEY`, `MAVEN_GPG_PASSPHRASE`) and in the App settings (`RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`).

The weekly `.github/workflows/credential-reminder.yml` (`Credential reminder`) runs in a job of the `release` environment, so it reads `SONAR_TOKEN`, `CENTRAL_USERNAME`, `CENTRAL_PASSWORD` and `MAVEN_GPG_KEY` there. It also runs on manual request. It runs:

* `scripts/ci/check-sonar-token.py` and `scripts/ci/check-central-token.py`, which validate the Sonar and Central Portal tokens. A removed or revoked token fails the check with an explicit message instead of an unclear red build;
* `scripts/ci/check-credential-expiry.py`, which reads the expiry of the GPG key, the earliest `expirationDate` of all the user's SonarQube Cloud tokens (a token without one raises no reminder) and the dates (`YYYY-MM-DD`, set by the maintainer after each renewal) in the repository variables `CENTRAL_TOKEN_EXPIRES_ON` and `RELEASE_APP_KEY_EXPIRES_ON`. It opens or updates one renewal issue for a credential that expires within 30 days; the issue mentions the maintainer and carries the renewal steps.
