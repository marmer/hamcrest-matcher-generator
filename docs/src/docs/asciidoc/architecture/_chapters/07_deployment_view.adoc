== Deployment View

=== Infrastructure Level 1

The project has no runtime infrastructure of its own: the processor runs inside the compiler of the user's build. What
is deployed are the build artifacts and this documentation.

Motivation::

Users take the artifacts from Maven Central, and readers take the documentation from GitHub Pages. Both are produced
by automated builds, so no manual upload step exists.

Quality and/or Performance Features::

Every published jar is signed and comes with a sources jar and a Javadoc jar, which Maven Central requires. A
CycloneDX software bill of materials is attached to every published module, so users can see which dependencies it
brings along.

Mapping of Building Blocks to Infrastructure::

[options="header",cols="2,4"]
|===
| Building block | Deployed to

| `matcher-generator-annotations`, `matcher-generator-core`, `hamcrest-matcher-generator` and the two bridge jars
| Maven Central through the Central Portal.

| `*-endtoend-*` modules, `docs`
| Not published. The release bundle excludes them (`excludeArtifacts`).

| Documentation
| GitHub Pages, deployed by the `Docs` GitHub Actions workflow after the docs build and its link checks passed.
|===

=== Infrastructure Level 2

==== Release to Maven Central

The `release` Maven profile signs the jars with GPG, attaches the sources jar, the Javadoc jar and the CycloneDX SBOM,
and lets the `central-publishing-maven-plugin` upload one bundle to the Central Portal. The plugin publishes the
bundle automatically and waits until it is published. The former OSSRH is not used any more.

==== Documentation on GitHub Pages

The `Docs` workflow builds the `docs` module on JDK 21, uploads the rendered HTML as a Pages artifact and deploys it
with the official Pages actions. It runs for version tags and on manual request.

=== CI pipeline

Pull requests and pushes to `main` run these workflows on GitHub-hosted runners:

* `.github/workflows/ci-build.yml` (`CI-Build`) runs the jobs `Build` (`mvnw -B clean install -DskipTests`), `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25` and `Verify JDK latest` (the matrix; `latest` follows the newest GA JDK), `Release dry run` (the release profile with `verify`, then `scripts/ci/check-release-artifacts.sh`), `Mutation testing` (PIT, with a history cache keyed on the PIT version) and `Sonar` (validates `SONAR_TOKEN` with `scripts/ci/check-sonar-token.py` before the build, then runs the scanner with the quality gate), and `Example Gradle` (`mvnw -B -DskipEndtoend -DskipTests install`, then `gradlew build` in `example-gradle-java`, which resolves the reactor's artifacts from `mavenLocal()`).
* `.github/workflows/domain-docs-sync.yml` (`Domain docs in sync`) runs the domain docs check, the frozen 5.x suite check, `scripts/ci/check-project-version.py` (every module pom's own and parent version equals the manifest version, is an `extra-files` entry, and project dependencies have no literal version), `scripts/ci/check-workflow-hardening.py`, the unit tests of `scripts/ci` and `scripts/agents`, and the check of the ruleset's job names.
* `.github/workflows/dependency-review.yml` (`Dependency review`) runs on pull requests, `.github/workflows/scorecard.yml` (`Scorecard`) weekly and on pushes to `main`, and `.github/workflows/scanoss.yml` (`SCANOSS`) on pull requests and weekly. SCANOSS is non-blocking.
* `.github/workflows/credential-reminder.yml` (`Credential reminder`) runs weekly and on manual request, in a job of the `release` environment (so it reads `SONAR_TOKEN`, `CENTRAL_USERNAME`, `CENTRAL_PASSWORD` and `MAVEN_GPG_KEY` there). It validates the Sonar and Central Portal tokens (`scripts/ci/check-sonar-token.py`, `scripts/ci/check-central-token.py`), then `scripts/ci/check-credential-expiry.py` reads the expiry of the Sonar token and the GPG key and the expiry dates (`YYYY-MM-DD`, set by the maintainer after each renewal) in the repository variables `CENTRAL_TOKEN_EXPIRES_ON` and `RELEASE_APP_KEY_EXPIRES_ON`, and opens or updates one renewal issue for a credential that expires within 30 days.

The `main` ruleset requires `Build`, `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25`, `Verify JDK latest`, `Domain docs in sync`, `Release dry run`, `Sonar` and `Mutation testing`. `Example Gradle` is a blocking job of the same CI (a red job fails the workflow run) but not in the ruleset, so it is not required for a merge; adding it to the ruleset is an owner action. `scripts/ci/check-ruleset-job-names.py` only checks that every required name is a job name, so it does not demand that `Example Gradle` be added. `Dependency review`, `Scorecard` and `SCANOSS` are not required.

=== Release pipeline

Releases run on CI and need no machine of the owner.

* `.github/workflows/pr-title.yml` (required check `PR title`) enforces Conventional Commits on pull request titles, because the squash-merged title is the commit that release-please reads.
* `.github/workflows/release.yml` runs on every push to `main`. release-please (type `simple`, default bump rules, configured in `release-please-config.json` and `.release-please-manifest.json`) keeps a Release PR up to date, using an App token so that the PR runs its checks and the new tag triggers the docs deployment. Tags have no `v` prefix (`6.0.0`), matching the `[0-9]*` trigger of `docs.yml`.
The project version lives in the module poms (own and parent `<version>`), which release-please raises through one xml entry per pom in `extra-files`, and in the Gradle example (marker `x-release-please-version`). The `simple` type is used instead of `maven` because the Maven updater rewrites the `@project.version@` of the frozen 5.x suite and misses the parent versions. The `simple` type's optional `version.txt` is not created: its updater has `createIfMissing: false` and the release-please 17.11.2 simulation of the 6.0.0 release changed only `CHANGELOG.md`, the Gradle example and the 20 poms. Dependencies on project artifacts use `${project.version}`, the 5.x suite and its runner's consumer poms are filtered by the build (`@project.version@`). `scripts/ci/check-project-version.py` guards all of it.
* Merging the Release PR creates the tag and the release page. In the same workflow the job `Release build` runs `mvnw verify` on the tag, and only if it is green the job `Publish to Maven Central` runs `mvnw -P release deploy` (GPG signatures, SBOM, `central-publishing-maven-plugin` waiting for `published`), attaches a build-provenance attestation (`actions/attest`) and makes sure the release page exists.
* After a confirmed publish, the job `Announce release` comments on the merged Release PR with the App token, mentioning the owner and linking Maven Central, the release page and the CHANGELOG section.
* A failed publish is re-run with `workflow_dispatch` and the existing tag as input; tags are never moved.
* 6.0.0 is forced with `release-as` and merged by the owner. Auto-merge of Release PRs stays off until after 6.0.0.

The credentials live in the repository environment `release` (`CENTRAL_USERNAME`, `CENTRAL_PASSWORD`, `MAVEN_GPG_KEY`, `MAVEN_GPG_PASSPHRASE`) and in the App settings (`RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`).
