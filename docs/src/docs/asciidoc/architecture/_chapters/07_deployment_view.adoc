== Deployment View

=== Infrastructure Level 1

The project has no runtime infrastructure of its own: the processor runs inside the compiler of the user's build. What
is deployed are the build artifacts and this documentation.

Motivation::

Users take the artifacts from Maven Central, and readers take the documentation from GitHub Pages. Both are produced
by automated builds, so no manual upload step exists.

Quality and/or Performance Features::

Every published jar is signed and comes with a sources jar and a Javadoc jar, which Maven Central requires. A
CycloneDX software bill of materials is attached to every published module, so users can see which dependencies it
brings along.

Mapping of Building Blocks to Infrastructure::

[options="header",cols="2,4"]
|===
| Building block | Deployed to

| `matcher-generator-annotations`, `matcher-generator-core`, `hamcrest-matcher-generator` and the two relocation POMs
| Maven Central through the Central Portal.

| `*-endtoend-*` modules, `docs`
| Not published. The release bundle excludes them (`excludeArtifacts`).

| Documentation
| GitHub Pages, deployed by the `Docs` GitHub Actions workflow after the docs build and its link checks passed.
|===

=== Infrastructure Level 2

==== Release to Maven Central

The `release` Maven profile signs the jars with GPG, attaches the sources jar, the Javadoc jar and the CycloneDX SBOM,
and lets the `central-publishing-maven-plugin` upload one bundle to the Central Portal. The plugin publishes the
bundle automatically and waits until it is published. The former OSSRH is not used any more.

==== Documentation on GitHub Pages

The `Docs` workflow builds the `docs` module on JDK 21, uploads the rendered HTML as a Pages artifact and deploys it
with the official Pages actions. It runs for version tags and on manual request.

=== Release pipeline

Releases run on CI and need no machine of the owner.

* `.github/workflows/pr-title.yml` (required check `PR title`) enforces Conventional Commits on pull request titles, because the squash-merged title is the commit that release-please reads.
* `.github/workflows/release.yml` runs on every push to `main`. release-please (Maven mode, `skip-snapshot`, default bump rules, configured in `release-please-config.json` and `.release-please-manifest.json`) keeps a Release PR up to date, using an App token so that the PR runs its checks and the new tag triggers the docs deployment. Tags have no `v` prefix (`6.0.0`), matching the `[0-9]*` trigger of `docs.yml`.
* Merging the Release PR creates the tag and the release page. In the same workflow the job `Release build` runs `mvnw verify` on the tag, and only if it is green the job `Publish to Maven Central` runs `mvnw -P release deploy` (GPG signatures, SBOM, `central-publishing-maven-plugin` waiting for `published`), attaches a build-provenance attestation (`actions/attest`) and makes sure the release page exists.
* After a confirmed publish, the job `Announce release` comments on the merged Release PR with the App token, mentioning the owner and linking Maven Central, the release page and the CHANGELOG section.
* A failed publish is re-run with `workflow_dispatch` and the existing tag as input; tags are never moved.
* 6.0.0 is forced with `release-as` and merged by the owner. Auto-merge of Release PRs stays off until after 6.0.0.

The credentials live in the repository environment `release` (`CENTRAL_USERNAME`, `CENTRAL_PASSWORD`, `MAVEN_GPG_KEY`, `MAVEN_GPG_PASSPHRASE`) and in the App settings (`RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`).
