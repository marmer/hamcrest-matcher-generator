== Risks and Technical Debts

After 6.0.0 the project is meant to run on autopilot: bots update dependencies, merge green pull requests and publish releases, and the maintainer only steps in when something turns red.
The risks below are the ways this can stall or go wrong; the technical debts are deliberate compromises the architecture carries.

Each entry is rated on two scales:

* *Probability* that the risk occurs, or that the debt causes harm: _low_ (1), _medium_ (2) or _high_ (3).
* *Impact* if it does: _tolerable_ (1, a nuisance that does not stop development or users), _disabling_ (2, merges, releases or a feature stop until someone acts; recoverable) or _catastrophic_ (3, harm that cannot be undone, such as a malicious release signed with the project's key).

The list is ordered by priority, the product of both values, highest first; entries with the same product are ordered by urgency.

[options="header",cols="3,1,1,5,5"]
|===
|Risk or technical debt |Probability |Impact |Description |Measures

|Risk: credentials expire
|medium
|disabling
|The autopilot depends on four credentials: the SonarCloud token (a personal token with no fixed validity period, which SonarCloud removes after 60 days without use), the GPG signing key (three years), the Maven Central Portal token (from the legacy username/password account) and the private key of the GitHub App that creates release pull requests. When one expires or is revoked, either every merge stops (Sonar is a required check) or releases fail.
|A weekly reminder workflow (`credential-reminder.yml`) validates the Sonar token and the Central token and reads the expiry of the GPG key and the Sonar token's `expirationDate` (the earliest among the user's tokens, because the API does not tell which one is `SONAR_TOKEN`); the Sonar token has no expiry date, so it raises no Sonar reminder, and the 60-day limit is covered by the CI runs and the weekly check that keep it in use; the Central token and the App key have their expiry dates in repository variables. 30 days before an expiry it opens or updates an issue that mentions the maintainer; the issue itself carries the renewal steps. The validation also catches a removed or revoked Sonar token, and CI runs keep it in use. Invalid credentials fail with an explicit message instead of an unclear red build. The maintainer runbook (`MAINTAINING.md`) lists every credential, where it is stored and how to renew it.

|Risk: free external services change or fail
|medium
|disabling
|The project relies on services that are free for open-source projects: GitHub Actions and Pages, SonarCloud, the Mend Renovate app, the Maven Central Portal and release-please. Any of them may change its terms, rate-limit (the free Renovate app already runs only every few hours) or be unavailable. Because Sonar is a required check, a SonarCloud outage blocks every merge.
|Accepted. All required checks are the project's own workflow jobs, not checks posted by the vendors, so a failing service shows up as a clearly named red job. During an outage the maintainer may merge past the ruleset. Fallbacks are known: Renovate can run self-hosted in GitHub Actions, and the Sonar job can be made non-blocking.

|Risk: JDK internals break the newest JDK leg
|medium
|disabling
|The annotation processor's integration tests compile code in memory with Google Compile Testing, which needs `--add-opens` access to the JDK's internal compiler packages. A future JDK may close that access or change the language model (`javax.lang.model`), for example for value classes. The `Verify JDK latest` check is required, so such a break blocks every merge, not only the JDK update itself.
|Renovate moves the `latest` leg to each new JDK in its own pull request, so a break is visible within days of the release and attributable to the JDK (<<qs-b2,QS-B2>>). The fallback is to compile the test sources with the plain `javax.tools` compiler API instead of Compile Testing.

|Risk: a single maintainer
|medium
|disabling
|Every red pull request, credential renewal and baseline decision lands on one person. If the maintainer is unavailable, updates stop and users receive no fixes. Nothing broken gets merged, because red pull requests wait.
|Accepted. The autopilot keeps routine work away from the maintainer. A maintainer runbook (`MAINTAINING.md`) gives the playbooks for these failures, so that anyone with admin rights, or an AI agent session, can act.

|Risk: the Java baseline erodes again
|medium
|disabling
|6.0.0 requires Java 17 (link:{adr-url}/0005-java-17-baseline.md[ADR 0005]). Libraries and tools keep raising their own minimum; Structurizr and Error Prone already need Java 21. When a dependency on the users' classpath or a build tool needed on the JDK 17 leg requires a newer Java version, its update cannot be merged automatically.
|The case shows up as one red Renovate pull request (Maven Enforcer's bytecode check or the JDK 17 leg). The maintainer either caps that dependency in the Renovate configuration with a comment naming the reason, or raises the baseline in a new major version. Tools that are only needed for analysis or documentation run in the JDK 21+ profile and do not affect the baseline.

|Risk: a compromised dependency is released automatically
|low
|catastrophic
|Green pull requests are merged without a human, and releases are published without one. A malicious version of a dependency or a GitHub Action that passes every check would be released to Maven Central, signed with the project's GPG key, and reach every user who updates.
|Renovate waits until a version is at least three days old (`minimumReleaseAge`), so most withdrawn or compromised releases never get proposed. Actions are pinned by commit SHA, workflow permissions are minimal, dependency review blocks known vulnerabilities, and OpenSSF Scorecard reports the repository's posture weekly. Every release carries a build-provenance attestation and an SBOM, so users can trace what was built from which commit, and every release notifies the maintainer.

|Technical debt: the 5.x compatibility layer stays forever
|high
|tolerable
|To let 5.x users upgrade by a version bump, 6.0.0 keeps the deprecated `@MatcherConfiguration` annotation as an alias, bridge jars for the changed artifacts and the 5.x method names such as `resetFoo` (link:{adr-url}/0002-coordinates-packages-and-5x-compatibility.md[ADR 0002]). As 6.0.0 is the final feature release, there is no later major version that would remove them.
|Accepted. The frozen 5.x suite (consumer build `endtoend-5x-compatibility-runner`, tree hash guarded) keeps the layer working (<<qs-x2,QS-X2>>); the deprecated alias is the only code in the old package.

|Technical debt: the Kotlin DSL backend depends on the Hamcrest backend
|high
|tolerable
|The architecture keeps backends independent of each other: each one depends only on the core. The Kotlin DSL backend is a deliberate exception. It builds on the Hamcrest backend and reuses its naming of the generated matchers (`XMatcher`, `isX`, `withFoo`, `ignoringFoo`). A change to that naming therefore breaks the generated Kotlin code, and the two modules cannot evolve independently (link:{adr-url}/0004-kotlin-dsl-backend-on-top-of-hamcrest.md[ADR 0004]).
|The exception is allowed for exactly this one dependency, and Maven Enforcer and an ArchUnit test reject any other dependency between backends. Golden-file tests of the generated Kotlin code and the Kotlin end-to-end modules fail as soon as the Hamcrest naming changes without the DSL following it.

|Risk: a release builds with a wrong module version
|low
|disabling
|The release type `simple` with one explicit `extra-files` entry per module pom (see <<section-deployment-view,chapter 7>>) was only verified by a simulation with the updaters of release-please 17.11.2, never by a real release-please run, because the development sandbox cannot call the GitHub API. The first real Release PR after this change is the first real test. A new module pom without an `extra-files` entry is caught by `scripts/ci/check-project-version.py` in the required job `Domain docs in sync`. It is assumed, not verified, that the checks also run on the Release PR, because the GitHub App token creates it.
|`scripts/ci/check-project-version.py` runs on the Release PR and turns a wrong one red before the release. The maintainer looks at the first Release PR after the change before merging it: own and parent version 6.0.0 in every module pom, and the pom of the frozen 5.x suite still `@project.version@`. The playbook "Red Release pull request" in `MAINTAINING.md` applies.

|Risk: the Kotlin DSL needs KAPT
|low
|disabling
|The Kotlin DSL is only generated when the annotation processor runs under KAPT, the Kotlin compiler's way of running Java annotation processors. JetBrains puts its new development into KSP, which is out of scope for this project. If a future Kotlin release dropped KAPT, the DSL could no longer be generated.
|The DSL is optional: the generated Java matchers work from Kotlin without it, and they do not depend on KAPT. Renovate keeps the tested Kotlin version current, so a removal of KAPT shows up as a failing update instead of a surprise for users.

|Risk: strict quality gates stop the autopilot
|medium
|tolerable
|Merges require at least 99 % line and branch coverage. The CI jobs `Mutation testing` (a mutation score of at least 90 % per module) and `Sonar` (the quality gate) are required merge checks of the `main` ruleset, so a red one blocks the merge. An update of PIT or JaCoCo (new mutators, different branch counting) or a change of SonarCloud's rules can turn a pull request or the main branch red although no project code changed.
|PIT, JaCoCo and the Sonar scanner are updated in their own Renovate pull requests, so the cause of a red build is unambiguous. The Sonar quality gate judges new code only, so new rules do not fail old code. Thresholds are never lowered silently; a change goes to the maintainer.

|Risk: a major update of a runtime dependency ships as a patch release
|low
|tolerable
|Renovate merges major updates of the libraries on the users' classpath (Hamcrest, AssertJ, JSpecify) automatically, as `fix(deps)` commits, which release-please publishes as a patch release. Users therefore receive a new major version of such a library transitively with a patch release of this project, and an API change in it may break their own tests.
|Accepted. The end-to-end modules exercise the generated code against the new version before it is released, Maven Enforcer rejects a dependency that needs a newer Java version, and the release notes generated by release-please name the dependency update. Users can pin the library version in their own build.

|Risk: the generator's run time is not measured
|low
|tolerable
|Scenario <<qs-x5,QS-X5>> asks that generating assertions for 200 configured types adds at most 2 seconds to a compilation. No check measures this, so a change that slows down the annotation processor would go unnoticed until users complain about slow builds.
|The risk is accepted: projects configure far fewer types than that, and a run-time check on shared CI runners would produce unreliable results. Should users report slow builds, a benchmark module can be added later.

=== Accepted OpenSSF Scorecard findings

The OpenSSF Scorecard (`.github/workflows/scorecard.yml`) reports the repository's posture; its score does not gate merges. The table below lists every Scorecard check that was accepted instead of fixed, with the reason and the owner's decision. It is separate from the table above, because a Scorecard check measures a practice and not a risk that occurs, so the probability and impact scales do not apply. The entries rest on the Scorecard API result of 2026-10-31 (analysed commit `95d1727`, Scorecard v5.6.0, total score 7.7) and on the ruleset as the owner left it. The date is the owner's decision where one is recorded, otherwise the date of that result.

`Fuzzing` (score 0 on 2026-10-31) has no entry: the project has a Jazzer fuzz test (`ItemsInAnyOrderFuzzTest`), and an entry is written only if a weekly Scorecard run after it still reports 0.

CII-Best-Practices (score 0) has no entry yet: the badge registration (issue #284) is still open. It gets an entry only after the owner has decided the unmet criteria of the passing level.
