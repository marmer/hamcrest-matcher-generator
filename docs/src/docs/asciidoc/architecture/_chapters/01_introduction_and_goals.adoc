== Introduction and Goals

hamcrest-matcher-generator is an annotation processor for Java and Kotlin projects. A test developer names the configured
types (beans and records) in a `@GenerateMatchers` annotation, and the processor generates type-safe Hamcrest matchers
and AssertJ assertions for their properties while the project compiles. The configured types stay untouched. This chapter
states what the system has to do, which qualities matter most and who cares about it. The five quality goals, in priority
order, are correctness, non-intrusiveness, usability, build-tool agnosticism and maintainability
(<<section-quality-goals,Quality Goals>>); <<section-quality-scenarios,chapter 10>> refines each of them into measurable scenarios.

=== Requirements Overview

* Hamcrest matchers for configured types (beans and records), generated at compile time (<<section-runtime-view,chapter 6>>)
* Configured types stay untouched: one annotation on a separate configuration class (<<strategy-non-intrusiveness,chapter 4>>)
* A compile-safe alternative to Hamcrest's `hasProperty()` (link:../guide/hamcrest-backend.html[Hamcrest backend guide])
* Informative mismatch messages (<<runtime-mismatch-hamcrest,chapter 6>>)
* Lombok-annotated classes are supported (link:../guide/configuration.html[configuration guide])
* Plain Java and Kotlin, the latter via KAPT (link:../guide/kotlin.html[Kotlin guide])

.Planned feature set of 6.0.0, the final feature release
Version 6.0.0 adds a second backend for AssertJ next to Hamcrest. Both are driven by the same configuration. Its features are:

* *Completeness check* (both backends): every property of a type is checked or consciously ignored, opt-in per assertion (link:../guide/completeness-check.html[completeness check guide]).
* *Reference-object matcher* (Hamcrest): compares a whole object with a reference object, with overrides; AssertJ users get the same with its recursive comparison (link:../guide/hamcrest-backend.html[Hamcrest backend guide], link:../guide/assertj-backend.html[AssertJ backend guide]).
* *Readable mismatches* (Hamcrest): one line per failing check with its property path and both values (<<runtime-mismatch-hamcrest,chapter 6>>, link:../guide/mismatch-messages.html[mismatch messages]).
* *Collection matchers* (Hamcrest runtime): `itemsInOrder(...)`, `itemsInAnyOrder(...)` and `entries(...)` check every item or entry; Hamcrest's own collection matchers keep working but print Hamcrest's less specific messages (link:../guide/mismatch-messages.html[mismatch messages]).
* *AssertJ messages* keep AssertJ's own wording and name the property path (link:../guide/mismatch-messages.html[mismatch messages]).
* *Exclude configuration*: packages or classes can be excluded from generation, for every backend (link:../guide/configuration.html[configuration guide]).
* *Null-safety annotations* (JSpecify) in the generated code and the Hamcrest runtime, mainly for Kotlin (<<term-nullability,Nullability>>).
* *Clear compiler diagnostics*: errors and warnings at the annotation that configured the type (<<concepts-diagnostics,chapter 8>>).
* *Kotlin support*: Kotlin boolean and `is`-prefixed properties, and a Kotlin DSL (link:../guide/kotlin.html[Kotlin guide]).
* *Java module names*: every published jar declares an `Automatic-Module-Name` (<<section-deployment-view,chapter 7>>).
* *AssertJ assertions* with `hasFoo`, `hasFooSatisfying`, `isFoo`/`isNotFoo`, an `InstanceOfAssertFactory` per type and soft-assertion support (link:../guide/assertj-backend.html[AssertJ backend guide]).

After 6.0.0 no further features are planned; the project receives only fixes and automated dependency updates.

[[section-quality-goals]]
=== Quality Goals

[options="header",cols="1,2,4,2"]
|===
| Priority | Quality | Motivation | Scenarios

| 1
| Correctness
| Generated assertions (Hamcrest matchers and AssertJ assertions) must be type-safe, compile without errors and fail exactly when the checked object is wrong: no false green tests; broken generation is worse than no generation
| <<qs-c1,QS-C1>>, <<qs-c2,QS-C2>>, <<qs-c3,QS-C3>>, <<qs-c4,QS-C4>>, <<qs-x3,QS-X3>>, <<qs-x4,QS-X4>>

| 2
| Non-intrusiveness
| The core design promise: the configured types stay untouched and the processor adds no runtime dependency to production code; the annotation has `SOURCE` retention, see <<section-solution-strategy,chapter 4>>
| <<qs-n1,QS-N1>>, <<qs-n2,QS-N2>>, <<qs-n3,QS-N3>>, <<qs-x1,QS-X1>>, <<qs-x5,QS-X5>>

| 3
| Usability
| The generated assertions (Hamcrest matchers and AssertJ assertions) must be discoverable and ergonomic for test writers
| <<qs-u1,QS-U1>>, <<qs-u2,QS-U2>>, <<qs-u3,QS-U3>>, <<qs-u4,QS-U4>>

| 4
| Build-tool agnosticism
| Works via standard APT (javac) and KAPT (kotlinc); no coupling to a specific build plugin
| <<qs-b1,QS-B1>>, <<qs-b2,QS-B2>>, <<qs-x2,QS-X2>>

| 5
| Maintainability
| The processor codebase must remain understandable and extensible for contributors
| <<qs-m1,QS-M1>>, <<qs-m2,QS-M2>>, <<qs-m3,QS-M3>>, <<qs-m4,QS-M4>>
|===
