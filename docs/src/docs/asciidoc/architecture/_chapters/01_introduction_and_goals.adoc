* Generate Hamcrest matchers for model/domain classes at compile time
* No production-code pollution - configuration uses a SOURCE-retention annotation only, leaving model classes untouched
* Compile-safe alternative to Hamcrest's `hasProperty()` / `HasPropertyWithValue`
* Informative mismatch messages via the generated fluent API
* Lombok-annotated classes are supported
* Works with plain Java and Kotlin (via KAPT)

.Planned feature set of 6.0.0, the final feature release
Version 6.0.0 adds a second backend for AssertJ next to Hamcrest. Both are driven by the same configuration. Its features are:

* *Completeness check* (the lead feature, for both backends): every property of a type is either checked or deliberately ignored. Users opt in per assertion and the check runs when the test runs: Hamcrest matchers offer `checkingAllProperties()`, AssertJ assertions offer the scope `satisfiesCheckingAllProperties(...)` and the closing call `hasAllPropertiesChecked()`, and `ignoringFoo()` marks a property as deliberately ignored. Without the opt-in, matchers behave as in 5.x.
* *Reference-object matcher* (Hamcrest): compares a whole object against a reference object and allows single properties to be overridden or reset. The comparison goes deep: a nested value whose type has a generated matcher is compared property by property, a list item by item in order, any other collection in any order, and a map key by key. Everything else is compared with `equals`. AssertJ users get the same with AssertJ's built-in recursive comparison, which the documentation shows side by side.
* *Readable mismatches* (Hamcrest): only the failing checks are listed, one per line, each with its property path and both values, for example `customer.address.city: expected "Berlin" but was "Paris"`. Paths reach into lists (`lines[1].quantity`) and maps (`bySku["B-2"].quantity`); missing and unexpected items or keys get their own line. A generated matcher used inside one of Hamcrest's own matchers, such as `contains(...)`, prints on a single line. Values of generated types are shown with their properties instead of their `toString()`.
* *Collection matchers* (Hamcrest runtime): `itemsInOrder(...)`, `itemsInAnyOrder(...)` and `entries(...)` check every item of a list or collection, or every entry of a map, and produce the paths above. Hamcrest's own collection matchers keep working but print Hamcrest's less specific messages.
* *AssertJ messages* keep AssertJ's native `Expecting ... to be ... but was ...` style and name the property path from the asserted object, for example `Expecting Order.customer.address.city to be: "Berlin"`. Inside a collection or map, the path starts again at the element type, because AssertJ reports the element's index itself. An optional generated `Representation` shows generated types with their properties in AssertJ's own messages.
* *Exclude configuration*: packages or classes can be excluded from generation, for every backend.
* *Null-safety annotations* (JSpecify) in the generated code and the Hamcrest runtime, which mainly makes the API type-safe for Kotlin.
* *Clear compiler diagnostics*: errors for unresolvable names and generated method names that clash with inherited ones, warnings for configured types without properties and for exclusions that match nothing.
* *Kotlin support*: correct detection of Kotlin boolean and `is`-prefixed properties, and a Kotlin DSL.
* *Java module names*: every published jar declares an `Automatic-Module-Name`.
* *AssertJ assertions* with `hasFoo`, `hasFooSatisfying`, `isFoo`/`isNotFoo`, an `InstanceOfAssertFactory` per type and soft-assertion support.

After 6.0.0 no further features are planned; the project receives only fixes and automated dependency updates.

=== Quality Goals

[role="arc42help"]
****
.Contents
The top three (max five) quality goals for the architecture whose fulfillment is of highest importance to the major stakeholders.
We really mean quality goals for the architecture.
Don't confuse them with project goals.
They are not necessarily identical.

.Motivation
You should know the quality goals of your most important stakeholders, since they will influence fundamental architectural decisions.
Make sure to be very concrete about these qualities, avoid buzzwords.
If you as an architect do not know how the quality of your work will be judged …

.Form
A table with quality goals and concrete scenarios, ordered by priorities
****

[options="header",cols="1,2,4,2"]
|===
| Priority | Quality | Motivation | Scenarios

| 1
| Correctness
| Generated assertions (Hamcrest matchers and AssertJ assertions) must be type-safe, compile without errors and fail exactly when the checked object is wrong: no false green tests - broken generation is worse than no generation
| <<qs-c1,QS-C1>>, <<qs-c2,QS-C2>>, <<qs-c3,QS-C3>>, <<qs-c4,QS-C4>>

| 2
| Non-intrusiveness
| The core design promise: zero footprint on production code; SOURCE retention means no runtime dependency bleeds into model classes
| <<qs-n1,QS-N1>>, <<qs-n2,QS-N2>>, <<qs-n3,QS-N3>>

| 3
| Usability
| The generated assertions (Hamcrest matchers and AssertJ assertions) must be discoverable and ergonomic for test writers
| <<qs-u1,QS-U1>>, <<qs-u2,QS-U2>>, <<qs-u3,QS-U3>>, <<qs-u4,QS-U4>>

| 4
| Build-tool agnosticism
| Works via standard APT (javac) and KAPT (kotlinc); no coupling to a specific build plugin
| <<qs-b1,QS-B1>>, <<qs-b2,QS-B2>>

| 5
| Maintainability
| The generator codebase must remain understandable and extensible for contributors

=== Stakeholders

* should know the architecture
* have to be convinced of the architecture
* have to work with the architecture or with code
* need the documentation of the architecture for their work
* have to come up with decisions about the system or its development

.Motivation
You should know all parties involved in development of the system or affected by the system.
