Motivation::

The processor is split so that everything that is independent of an assertion library lives once, in the core, while
every assertion library is a backend that plugs in from the outside. A user chooses libraries by choosing artifacts
(see <<adr-0001,ADR 0001>>).

Contained Building Blocks::

[options="header",cols="2,4"]
|===
| Building block | Responsibility

| `matcher-generator-annotations`
| The configuration annotation `@GenerateMatchers` and its deprecated 5.x alias `@MatcherConfiguration`.

| `matcher-generator-core`
| The processor entry point, the discovery of configured types, the library-agnostic `TypeModel` and `PropertyModel`,
diagnostics, and the `GeneratorBackend` interface. It has no assertion library on its classpath.

| `hamcrest-matcher-generator`
| The Hamcrest backend: it turns a `TypeModel` into the source of a `<Type>Matcher` class with JavaPoet. It also
contains the runtime class `BeanPropertyMatcher` that the generated matchers call at test time and that builds the
mismatch messages, and the collection matchers: the factories in `CollectionMatchers` (`itemsInOrder`, `itemsInAnyOrder`,
`entries`) return `ItemsInOrder`, `ItemsInAnyOrder` and `Entries`, which share the package-private base type
`PathAwareMatcher`; `BeanPropertyMatcher` flattens them into indexed and keyed property paths. The walk along these
paths and the rendering of its findings live in the package-private `PathWalk` and `MismatchReport`, which both
`BeanPropertyMatcher` and the collection matchers use. `ReferenceMatching` is what the generated `isXLike(reference)` methods call: it presets the checks of a reference object (`BeanPropertyMatcher.preset`), builds one matcher per reference object while a matcher is built, so a cyclic graph yields a cyclic matcher, and `BeanPropertyMatcher` counts a pair of matcher and item met again as equal. The package-private `ReferencePresetPlanner` chooses, for each property of a reference object, the helper that compares it (the rule is in <<section-runtime-view,chapter 6>>). The opt-in completeness check (`checkingAllProperties()`) is also in `BeanPropertyMatcher`: a property is addressed when a check or `ignoringFoo()` names it, `resetFoo()` removes both, and the properties that are neither are reported after the failing checks. Every generated matcher extends `TypeSafeMatcher`, implements the public interface
`GeneratedBeanMatcher` (its `beanPropertyMatcher()` is the seam through which a generated matcher used as a property
check of another one is flattened into property paths; it is public because generated code lives in the user's
packages) and passes each property to the `BeanPropertyMatcher` constructor with the accessor that reads it, as
`BeanPropertyMatcher.property("name", (Type bean) -> bean.getName())` in declaration order, the lambda stating the type so that a static method overloading the getter does not make it ambiguous. The constructor that takes only the names is kept for matchers that an
older version generated; which reflection remains is listed in <<section-solution-strategy,chapter 4>>.

| `assertj-assertion-generator`
| The AssertJ backend: it turns a `TypeModel` into an abstract assertion class and a concrete assertion class per
configured type, with JavaPoet, and writes one soft assertions mixin and one representation per package. It is described
in text in <<building-block-assertj,White Box `assertj-assertion-generator`>>.

| `hamcrest-matcher-generator-kotlin`
| The opt-in Kotlin DSL backend (<<adr-0004,ADR 0004>>): one `<Type>MatcherDsl.kt` per configured type with properties,
written with KotlinPoet. It is the one backend that depends on another backend, the Hamcrest one. It is described in
text in <<building-block-kotlin,White Box `hamcrest-matcher-generator-kotlin`>>.

| `hamcrest-matcher-generator-dependencies`, `hamcrest-matcher-generator-annotationprocessor`
| Bridge jars with no functionality that depend on `hamcrest-matcher-generator`, so builds that name a 5.x artifact find a jar and get the Hamcrest backend transitively (see <<adr-0002,ADR 0002>>).

| `*-endtoend-*` modules
| Apply the processor to real beans and records, in plain Java, Kotlin and mixed projects, and exercise the generated
matchers in ordinary tests.

| `example-maven-java-hamcrest`, `example-maven-java-assertj`, `example-maven-kotlin`, `example-gradle-java`
| Documentation examples for the guide and README: Maven Java for each backend, Maven Kotlin with KAPT and the Kotlin DSL,
and a Gradle build outside the reactor with its own wrapper. They are never published; the Gradle build resolves the
reactor's artifacts from `mavenLocal()`.

| `docs`
| Renders this documentation to HTML and checks its internal links. It is built only on JDK 21 or later and is not
published to Maven Central.
|===

[[building-block-important-interfaces]]Important Interfaces::

Every backend implements the `GeneratorBackend` interface of the core, which is the only interface between the core and a backend. A backend receives a `TypeModel` and a `GenerationContext`, and returns its `GeneratedSource` files, each a Java or Kotlin file (per type, the Hamcrest backend returns one, the AssertJ backend two plus its per-package files, the Kotlin DSL backend one Kotlin file, or none). The `GenerationContext` carries:

* the generator name;
* whether JSpecify resolves at compile time (`jspecifyAvailable`), which is the condition for emitting JSpecify annotations;
* the models of all types generated in the run, so that generated code can refer to the code of another type;
* the names of the methods of a class on the compile class path, inherited ones included (`inheritedMethodNames`);
* `reportError` for a compiler error at the annotation (see <<concepts-diagnostics,chapter 8>>);
* whether Kotlin output is available (`kotlinOutputAvailable`);
* `reportNote` for a compiler note;
* `reportVerboseNote` for a compiler note that is only printed with `matchergenerator.verbose`;
* `classExistsOutsideOwnOutput` for whether a class is on the class path without being in this compilation's own output;
* `reportWarning` for a compiler warning.

Backends are discovered with `java.util.ServiceLoader` from the processor path, and every backend found runs for every
configured type. The core has no compile dependency on any backend, so it loads them only at run time. Backends depend only on the core, never the other way round, with one exception: the Kotlin DSL backend depends on the Hamcrest backend. The Enforcer plugin and ArchUnit tests
guard this.

The backend interface is internal to the project. `GeneratorBackend`, `GenerationContext`, `GeneratedSource` and the property model
(`TypeModel`, `PropertyModel`, `Nullability`, and the helper `TypeHierarchy` of the same package) are used by the project's own backends only. They make no stability promise and may change in any
release, including a patch release. The package Javadoc
of `core.spi` and `core.model` says the same, and <<adr-0001,ADR 0001>> records the amendment.

=== Level 2

The core and the Hamcrest backend have a component view, shown below. The AssertJ and Kotlin backends are small, so they are described in text only.

==== White Box `matcher-generator-core`

----
include::../workspace.dsl[]
----

`MatcherGenerationProcessor`::
The annotation processor (package `io.github.marmer.matchergenerator.core`) registered through `META-INF/services`. It loads the backends and hands every round to the
worker. It declares the processor option `kapt.kotlin.generated`.

`MatcherGenerationProcessorWorker`::
Plans the types of a round: it asks `ConfiguredNames` and `TypeExpansion` which types the configuration stands for, skips
types that are already marked as generated, models the rest, and asks every backend for its source, which it hands to the
source writer. It remembers the unresolved names of a configuration between rounds (see <<runtime-deferred-names,chapter 6>>).
Two small package-private records carry its data: `ConfigurationSite` (the configuration class and its annotation, which
a diagnostic points at) and `PlannedType` (a type with its model and the `ConfigurationSite` that asked for it).

`ConfiguredNames`::
The names that one configuration lists in its `value` attribute and its `exclude` attribute, and what they stand for in
the round: which names match a type or a package, and which exclusions name a type. It lives for one round, with the
compiler's `Elements` as its only seam; the names that matched nothing are kept from round to round as strings.

`TypeExpansion`::
Expands the configured names to the types to plan, with the excluded types left out and the public member types
included, and finds the exclusions that name none of them. It does not plan or generate; that is the worker's concern.

`ProcessorDiagnostics`::
Holds the texts of the messages the worker and the source writer give and places each one through the compiler's
`Messager`, at the element and annotation it names; the worker decides which message applies. Apart from verbose notes,
this is where the worker path calls the `Messager`: verbose notes go through `ElementSupport.logNote`, which the model
factory uses as well.

`GeneratedSourceWriter`::
Owns the `Filer`. It writes each source a backend returns, Java through the `Filer` and Kotlin into the directory named
by the processor option `kapt.kotlin.generated`, and keeps the rule for files written once per compilation (see
<<files-once-per-package,Files Written Once per Package>>).

`TypeModelFactory`::
Reads a type with the compiler's element API and creates the `TypeModel`: getters for beans, components and accessors
for records, inherited properties and public member types. The type of a property is the return type of its accessor
as a member of the configured type (`Types.asMemberOf`), so a type argument that a subtype gives its supertype
replaces the supertype's type variable: `Sub extends Base<String>` gives `String` for an inherited `T getValue()`.
A getter that declares a checked exception stays a property and is marked as such on its `PropertyModel`. Generated code
has no handler for that exception, so the backends call such a getter through a helper that turns the exception into the
failure a check reports, `Could not read property 'name'` with the exception as cause: `PropertyAccess.call` in the
Hamcrest backend, which the reference presets reach through `ReferenceMatching.read`, and `PropertyRead.of` in the AssertJ assertions and the property representation. The two are separate copies, because the AssertJ backend does not depend on the Hamcrest one (<<adr-0001,ADR 0001>>).
Unchecked exceptions and errors need no helper, so their getters are called directly, as before.

`NullabilityResolver`::
Derives the `Nullability` of a property for the `TypeModel`: primitives are non null, JSpecify and JetBrains
`@Nullable`/`@NonNull`/`@NotNull` on the accessor decide explicitly, and otherwise the closest `@NullMarked` or
`@NullUnmarked` scope does. A type variable is null-agnostic and stays unspecified. Kotlin nullness is read from the
JetBrains annotations kotlinc emits, not from `kotlin.Metadata`. The worker also sets the `GenerationContext` flag
that tells backends whether `org.jspecify.annotations.NullMarked` resolves, which is the condition for emitting
JSpecify annotations.

`TypeModel`, `PropertyModel`, `Nullability`::
The immutable model that backends work on (see the glossary term "<<term-property-model,Property model>>").

`TypeHierarchy`::
The one walk over a type's supertypes that the backends share (package `io.github.marmer.matchergenerator.core.model`).
It gives the direct supertypes of a type with the type variables of the type replaced by the type arguments it is given, and the element of a
declared type mirror. It only reads the `javax.lang.model` API; the Hamcrest backend binds type arguments with it, the AssertJ backend finds
iterable or map ancestors and counts ancestors with it. The model factory uses only its `asTypeElement`; its inherited-property walk stays its own,
because it also descends into supertypes that are not declared types (such as an error type), which `directSupertypes` leaves out.

==== White Box `hamcrest-matcher-generator`

.Components of hamcrest-matcher-generator
[structurizr,target=hamcrest-components,format=svg,view=HamcrestComponents,alt="Components of hamcrest-matcher-generator: the backend implements the SPI and delegates to the matcher generator, which generates code calling the runtime library, which extends Hamcrest TypeSafeMatcher",renderer=plantuml]
----
include::../workspace.dsl[]
----

`HamcrestGeneratorBackend`::
The Hamcrest implementation of `GeneratorBackend`, registered through `META-INF/services`. For every `TypeModel` it
asks `MatcherGenerator` for the `<Type>Matcher` source and returns it as one `GeneratedSource`.

`MatcherGenerator`::
Builds the source of a `<Type>Matcher` class with JavaPoet from a `TypeModel`: the `isX()` entry point, `withFoo`,
`resetFoo` and `ignoringFoo` for every property, `checkingAllProperties()` and the `isXLike(reference)` method. For the
presets of `isXLike(reference)` it asks `ReferencePresetPlanner`, which is described in the building block table above.

`BeanPropertyMatcher` and its helpers::
The runtime library that the generated matchers call at test time. It reads the checked properties of the actual object
through the accessor of each property (`BeanPropertyMatcher.Accessor`, a lambda or method reference such as
`Type::getName`, which may return `null` or throw an exception), collects the failing checks with their property paths and builds the mismatch message (see <<section-runtime-view,chapter 6>>). Its helpers, the
collection matchers (`itemsInOrder`, `itemsInAnyOrder`, `entries`), `ReferenceMatching`, `PathWalk` and `MismatchReport`,
are described in the building block table above. The library extends Hamcrest's `TypeSafeMatcher`. The values that a mismatch
message prints for a configured type are read through the accessors that the first matcher of the type registered. The reflection that remains is listed in <<section-solution-strategy,chapter 4>>.

[[building-block-assertj]]
==== White Box `assertj-assertion-generator`

The AssertJ backend turns a `TypeModel` into two classes with JavaPoet, `AbstractXAssert<SELF, ACTUAL>` on
`AbstractObjectAssert` and a concrete, non-final `XAssert` with a public constructor and a static `assertThat`. The
abstract class carries `hasFoo(value)` (deep equality) and `hasFooSatisfying(requirements)` for every property, and
`isFoo()` and `isNotFoo()` for boolean ones; all check first that there is an asserted object.

Every property also gets `ignoringFoo()`, and the abstract class has the opt-in completeness check: `satisfiesCheckingAllProperties(..)`
and `hasAllPropertiesChecked()`. The assertion object keeps the names it has addressed, and the check fails with the properties
that are neither addressed nor ignored, after the value checks have passed. The failure message and the path it names are described in <<runtime-mismatch-assertj,chapter 6>>. The scope form counts only the calls its requirements make, while the closing call counts the whole chain. The property names are a constant of the class.

Each concrete class has an `InstanceOfAssertFactory` constant for `as(X)` navigation.

Each target package gets one `SoftAssertionsProvider` mixin (written once per package, see <<files-once-per-package,chapter 6>> and <<adr-0006,ADR 0006>>) with a default `assertThat` and `then` per type,
so the generated assertions work as soft and BDD assertions. Each target package also gets one `PropertyRepresentation`, an AssertJ `StandardRepresentation` that prints configured types by their properties; the user registers it with `Assertions.useRepresentation`, and it is never registered automatically. Failures use AssertJ's own `Expecting ...` wording and name the property path from the root type. The runtime class `AssertionPath` carries
that path into the assertion of the value a `hasFooSatisfying` requirement is run for, matched by identity (its limits are in the glossary entry "<<term-assertion-path,Assertion path>>"); inside an array, collection or map the path
restarts at the element type. The runtime class `PropertyRead` reads a property whose getter declares a checked exception, for the assertions and the representation (the rule is under `TypeModelFactory` above). Name clashes in the generated code are reported as compiler errors (see <<concepts-diagnostics,chapter 8>>, Diagnostics).

Two package-private helpers serve the generators: `AssertionNaming` holds the names the generators and the name clash check
share (the mixin, the representation and the names of the assertion classes), as `MatcherNaming` does for the Hamcrest
backend, and `FileShell` gives every generated type the same `@Generated` annotation and null marking.

The generated code needs AssertJ on the test class path.

[[building-block-kotlin]]
==== White Box `hamcrest-matcher-generator-kotlin`

The opt-in Kotlin DSL backend (<<adr-0004,ADR 0004>>) writes one `<Type>MatcherDsl.kt` per configured type with properties next to the Java
matcher, with KotlinPoet from Java: an entry function `isOrder { }` and a scope class `OrderSpec` per type (nested types
included). It is the one backend that depends on another backend, the Hamcrest one, as stated in <<building-block-important-interfaces,Important Interfaces>>; the names of the Hamcrest matcher API come from the public class `MatcherNaming` of the Hamcrest
backend.

A nested type whose simple name another type of the package shares gets the names of its enclosing types in
front, such as `OuterInnerSpec` and `isOuterInner`; a top level type and every type without a clash keep their simple
name. The names depend on the set of types of the package only, not on their order, so the backend names them from the
models of all types generated in the run.
If the names that include the enclosing types still collide (a top level `NestedClashCustomer` next to
`NestedClash.Customer`), the backend does not pick a new name, since a name that depends on the other types of the
build would change when one of them is added. It reports one compiler error per group of colliding types at the
`@GenerateMatchers` annotation, naming all of them, and gives none of them a scope or an entry function; the rest of the
DSL is still written. The error is reported by the generation of the type that contains the first colliding type in
qualified name order, so it appears once, in whatever order the types are processed in. The types of all `@GenerateMatchers` configurations of one processing round are compared together; types generated in different rounds are never seen together, so a clash between them is not found.

The scope class is marked with `@MatcherDsl`, a Java annotation in this artifact that carries Kotlin's `@DslMarker`,
and delegates every call to the generated Java matcher, so mismatch messages are identical. A scope has
`name(value)`, `name(matcher)` and `ignoringName()` for every property, `checkingAllProperties()`, and `customer { }` for a
property whose type is a configured type that is compared deeply (neither an enum nor a type without properties). Java
types are written as their Kotlin counterparts (`String`, `Int`, `List<out T>`, a star projection for a type variable). A
type without properties gets no file. Without KAPT (`GenerationContext.kotlinOutputAvailable`
is false) the backend generates nothing and reports one compiler note through `GenerationContext.reportNote`. A property whose
name clashes with a member of the scope (`checkingAllProperties`, `delegate`, `block`, `matcher`) or with an `Any` member
(`equals`, `hashCode`, `toString`) gets no DSL functions and a compiler warning (see <<concepts-diagnostics,chapter 8>>, Diagnostics); the Java matcher keeps it, and the scope's `checkingAllProperties()` calls `ignoringX()` for it, so the completeness check does not wait for it. Kotlin keywords as property names are escaped with backticks. Collection and map properties
take the runtime collection matchers (`itemsInOrder`, `itemsInAnyOrder`, `entries`) whose items are the DSL's entry functions.
The generated Kotlin needs this artifact and `kotlin-stdlib` on the class path of the Kotlin compilation; it uses only Kotlin 1.9 language features.
