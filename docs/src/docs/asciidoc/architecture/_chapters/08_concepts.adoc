[[section-concepts]]

== Cross-Cutting Concepts

[[concepts-ci-gates]]
=== Continuous Integration Gates

Every push runs a small set of automated gates, and each one exists because a defect once reached the main branch or
blocked it. Pull requests and pushes to `main` run the workflows of the table on GitHub-hosted runners.

[options="header",cols="2,5"]
|===
| Gate | What it guarantees

| Build and verify matrix (`Build`, `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25`, `Verify JDK latest`)
a|
* `Build` runs `mvnw -B clean install -DskipTests -DskipITs`, then `mvnw -B verify`: the reactor installs without tests.
* The reactor builds in parallel: `.mvn/maven.config` sets `-T 1C`, so modules build side by side on the four cores of a runner (`clean verify` on JDK 21 was about 23 % faster in a local measurement). The release build, the release dry run, the `Mutation testing` job and the `Sonar` job pin `-T 1` and stay serial: signing and publishing are not worth the risk of a parallel build, the dry run has to behave like the release, the mutation gain was within run-to-run noise, and the Sonar goal was not tried in parallel mode.
* `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25` and `Verify JDK latest` run the build and verify matrix. `latest` follows the newest generally available JDK.
* Together they guarantee that `./mvnw clean verify` is green on every supported JDK, including the newest generally available one.

| JaCoCo floor (part of `Build and verify matrix`, checked in `verify`)
| Each of the five production modules (`matcher-generator-core`, `matcher-generator-annotations`, `hamcrest-matcher-generator`,
`assertj-assertion-generator`, `hamcrest-matcher-generator-kotlin`) has at least 99 % line and 99 % branch coverage. Unit and integration coverage are merged before the check, and no class is
excluded, so a drop below the floor fails `verify` on every JDK in the matrix. The bridge jars are not measured because they hold no code.

| Release dry run
| The `release` profile still builds through the deploy lifecycle with signing and publishing switched off. A script
checks that every published module has its jar, sources jar, Javadoc jar and CycloneDX bill of materials, and that
CycloneDX skipped no module. Nothing is uploaded.

| Mutation testing (`Mutation testing`)
a|
* PIT mutates the production code of four modules, named in the `--expect` list of the job: `matcher-generator-core`,
`hamcrest-matcher-generator`, `assertj-assertion-generator` and `hamcrest-matcher-generator-kotlin`. Each of them must detect
at least 90 % of its mutants (`mutationThreshold` 90, checked by `scripts/ci/pit-scores.py`). This tests the tests: a suite that stays green when the
code is broken fails the gate.
* The job keeps a history cache keyed on the PIT version.

| Sonar quality gate (`Sonar`)
a|
* `scripts/ci/check-sonar-token.py` validates `SONAR_TOKEN` before the build.
* SonarQube Cloud analyses the build and its quality gate fails the job when new code adds issues, duplicated or uncovered
code. Old code is not judged again when a rule changes.

| Example Gradle (`Example Gradle`)
a|
* The Gradle example outside the reactor builds against the artifacts of the reactor, so the guide's Gradle setup keeps
working on JDK 21 and on JDK 17, because users copy the example on both.
* The job validates the wrapper jar with the SHA-pinned `gradle/actions/wrapper-validation`, installs the reactor with `mvnw -B -DskipEndtoend -DskipTests -DskipITs install`, then runs `gradlew build` in `example-gradle-java` on JDK 21 and again on JDK 17. The example resolves the reactor's artifacts from `mavenLocal()`.
* The job has no Gradle dependency cache, because a cache is state that can differ between runs, and a 30-minute time limit. The wrapper distribution is pinned by `distributionSha256Sum`; only that distribution is cached (keyed on `gradle-wrapper.properties`), and the wrapper's `networkTimeout` is 60 seconds, so a slow download does not fail the check.

| Dependency review (`Dependency review`)
| The check fails on a pull request that adds a dependency with a known vulnerability.

| License gate (part of the Build and verify matrix)
| Every project dependency that a published jar needs uses a permissive license (Apache-2.0, MIT, BSD-2-Clause or
BSD-3-Clause); test-scope dependencies may also use EPL-1.0 or EPL-2.0. The `license-maven-plugin` fails the build on an
unknown or missing license, so a new dependency with an unseen license name must be added to the merge list on purpose.
Every published jar carries `META-INF/LICENSE`, `META-INF/NOTICE` and `THIRD-PARTY.txt`, which a per-module test checks.
Build plugins and the `docs` module's tooling are not checked.

| Static analysis (JDK 21+ profile `static-analysis`, part of `Verify JDK 21`, `Verify JDK 25` and `Verify JDK latest`)
a|
* Spotless checks google-java-format (AOSP style, 4-space indentation) and the SPDX header in every Java and Kotlin source
of the modules, including tests and end-to-end sources, except the frozen 5.x suite, which stays frozen and so carries no SPDX headers.
* Error Prone runs its default checks on every module at ERROR with no baseline.
* NullAway runs at ERROR in JSpecify mode on the `io.github.marmer` packages only: main, test and end-to-end sources in that package tree. The end-to-end POJOs in `foo.bar` are not NullAway-checked.
* Generated code is not checked and carries no license header.
* The JDK 17 leg skips the profile.

| [[concepts-frozen-5x-suite]]Frozen 5.x suite (part of `Domain docs in sync`)
a|
* The `endtoend-5x-compatibility` module is the one the 5.x promise was made with, frozen except for the owner-approved deviations (version references filtered by the consumer build). Its parent and own
version (`@project.version@`) follow the project version, as a 5.x user's version bump does.
* It is not a reactor module: `endtoend-5x-compatibility-runner` builds it as a consumer build with the invoker plugin against an isolated local
repository that holds the reactor artifacts, so Maven resolves the bridge jars like it does for a 5.x user, with the project's own compiler plugin version.
* The suite runs every test it has. Its `RelocationPomTest`, which asserted the former relocation POMs, was deleted with the owner's approval, and each bridge module tests its own shape (`BridgeJarIT`).
* Its tree hash must equal the stored one. Only the owner may update that hash.

| Ruleset against job names (part of `Domain docs in sync`)
| Every status check that the `main` ruleset requires is the name of an existing CI job, so a removed job cannot
block all merges.

| Docs sync (`Domain docs in sync`)
| The agent-facing glossary and ADRs are mirrored in these chapters, the required checks named in the agent docs are
CI job names, and the file names and packages that `CLAUDE.md` mentions exist.

| Versions and README snippets (part of `Domain docs in sync`)
| `scripts/ci/check-project-version.py` checks that every module pom's own and parent version equals the manifest version, is an `extra-files` entry, and that project dependencies have no literal version. `scripts/ci/sync-readme-snippets.py --check` fails when a README snippet no longer matches its tagged example region.

| Workflow hardening and script tests (part of `Domain docs in sync`)
| `scripts/ci/check-workflow-hardening.py`, and the unit tests of `scripts/ci` and `scripts/agents`, run in the same job.

| PR title (`PR title`, not a gate)
| Checks that the title of a pull request follows Conventional Commits.

| Scorecard (`Scorecard`, not a gate)
| Runs weekly and on pushes to `main`, and reports the repository's posture. Its score does not gate merges. The accepted findings are listed in <<concepts-scorecard-findings,Accepted OpenSSF Scorecard Findings>>.

| SCANOSS (`SCANOSS`, not a gate)
| Runs on pull requests and weekly. It is non-blocking.

| External links (`External links`, not a gate)
a|
* Runs weekly and on manual request. Its `lychee` job checks the external links of the rendered docs and opens or updates an issue for broken ones; it is non-blocking.
* Its `badges` job fails when a README badge is broken.

| Credential reminder (`Credential reminder`, not a gate)
| Validates the Sonar and Central tokens and warns before a credential expires; it is described with the credentials in <<deployment-credentials,chapter 7>>.
|===

[[concepts-diagnostics]]
=== Diagnostics

The core reports a misconfiguration as a compiler diagnostic at the annotation that configured the type. It reports
each problem once and names the offending value, such as unresolvable names.

* A backend that finds a problem in a configured type reports it the same way, through
`GenerationContext.reportError(message)`. The core prints the message as a compiler error at the `@GenerateMatchers`
annotation.
* The backend leaves the offending member out of its generated code, so the error is the only one the user sees.
* The AssertJ backend reports these problems:
** a generated method whose name an inherited AssertJ method already has: one error per property, naming the property
and the clashing methods;
** two properties that generate the same method name, such as a boolean `foo` and `notFoo`, both `isNotFoo()`: one error
per name;
** two nested types whose factory constants share a name, such as `FooBar` and `Foo_Bar`, both `FOO_BAR`: one error
per name;
** a top level class name that two types of one package need, such as `Foo` and `AbstractFoo`, both generating
`AbstractFooAssert`, or a type named like the package's mixin `SoftAssertionsProvider`: the backend then writes nothing
for the package.
* Names that only look alike do not clash: `FooBar`, `Foo_Bar` and `FOOBAR` are different classes.
* Like the other per-package files, the AssertJ backend sees only the types of one processing round
(see <<files-once-per-package,chapter 6>> and <<adr-0006,ADR 0006>>).

A backend that leaves something out of its generated code without failing the build reports it through
`GenerationContext.reportWarning(message)`: the core prints the message as a compiler warning at the same annotation. The
Kotlin DSL backend uses it for a property whose name clashes with a member of its DSL scope; that property is left out
of the DSL (what the DSL does with it is in <<building-block-kotlin,chapter 5>>).

The core warns about one kind of skipped getter as well. A getter with the `get` prefix that returns a boolean, such as
`boolean getActive()`, and an `is` method that does not return a boolean, such as `String isName()`, are no properties in
Java. When the configuration names the type itself, that skip is one compiler warning at the configured value that names
the type. A nested type counts when the configuration names it by its own qualified name; a nested type that comes with
its named container gets the verbose note instead. The warning has the text of the verbose note and says that the
completeness check does not see the getter, so no matcher checks its value. A type that only a package entry picks up
gets the verbose note instead, and so does every other skipped method, such as a private or a static one.

=== Accepted OpenSSF Scorecard Findings

The table below lists every Scorecard check that was accepted instead of fixed, with the reason and the owner's decision. It is separate from the risk table in <<section-technical-risks,chapter 11>>, because a Scorecard check measures a practice and not a risk that occurs, so the probability and impact scales do not apply. The entries rest on the Scorecard API result of 2026-10-31 (analysed commit `95d1727`, Scorecard v5.6.0, total score 7.7) and on the ruleset as the owner left it. The date is the owner's decision where one is recorded, otherwise the date of that result.

`Fuzzing` (score 0 on 2026-10-31) has no entry: the project has a Jazzer fuzz test (`ItemsInAnyOrderFuzzTest`), and an entry is written only if a weekly Scorecard run after it still reports 0.

CII-Best-Practices (score 0) has no entry yet. The project is registered and the README shows the OpenSSF Best Practices badge. The entry follows only after the owner has decided the unmet criteria of the passing level.
