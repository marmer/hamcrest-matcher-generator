[[section-concepts]]

== Cross-cutting Concepts

[[concepts-ci-gates]]
=== Continuous integration gates

Every push runs a small set of automated gates. Each one exists because a defect once reached the main branch or
blocked it. The checks the `main` branch ruleset requires before GitHub merges a pull request are listed in <<section-deployment-view,chapter 7>>.

[options="header",cols="2,5"]
|===
| Gate | What it guarantees

| Build and Verify matrix (`Build`, `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25`, `Verify JDK latest`)
| The reactor installs without tests, and `./mvnw clean verify` is green on every supported JDK, including the newest
generally available one.

| JaCoCo floor (part of `Build and Verify matrix`, checked in `verify`)
| Each production bundle (`matcher-generator-core`, `matcher-generator-annotations`, `hamcrest-matcher-generator`) has at
least 99 % line and 99 % branch coverage. Unit and integration coverage are merged before the check, and no class is
excluded, so a drop below the floor fails `verify` on every JDK in the matrix. The bridge jars are not measured because they hold no code (deliberate deviation from #126).

| Release dry run
| The `release` profile still builds through the deploy lifecycle with signing and publishing switched off. A script
checks that every published module has its jar, sources jar, Javadoc jar and CycloneDX bill of materials, and that
CycloneDX skipped no module. Nothing is uploaded.

| Mutation testing (`Mutation testing`)
| PIT mutates the production code of the published modules, and each module must detect at least 90 % of its mutants
(`mutationThreshold` 90, checked by `scripts/ci/pit-scores.py`). This tests the tests: a suite that stays green when the
code is broken fails the gate.

| Sonar quality gate (`Sonar`)
| SonarCloud analyses the build and its quality gate fails the job when new code adds issues, duplicated or uncovered
code. Old code is not judged again when a rule changes.

| Example Gradle (`Example Gradle`)
| The Gradle example outside the reactor builds against the artifacts of the reactor, so the guide's Gradle setup keeps
working on JDK 21 and on JDK 17 (see <<section-deployment-view,chapter 7>>).

| Dependency review (`Dependency review`, not a required check)
| A pull request that adds a dependency with a known vulnerability is blocked.

| License gate (part of the Build and verify matrix)
| Every project dependency that a published jar needs uses a permissive license (Apache-2.0, MIT, BSD-2-Clause or
BSD-3-Clause); test-scope dependencies may also use EPL-1.0 or EPL-2.0. The `license-maven-plugin` fails the build on an
unknown or missing license, so a new dependency with an unseen license name must be added to the merge list on purpose.
Every published jar carries `META-INF/LICENSE`, `META-INF/NOTICE` and `THIRD-PARTY.txt`, which a per-module test checks.
Build plugins and the `docs` module's tooling are not checked.

| Static analysis (JDK 21+ profile `static-analysis`, part of `Verify JDK 21`, `Verify JDK 25` and `Verify JDK latest`)
| Spotless checks google-java-format (AOSP style, 4-space indentation) and the SPDX header in every Java and Kotlin source
of the modules, including tests and end-to-end sources, except the frozen 5.x suite, which stays frozen and so carries no SPDX headers (deliberate deviation from #128). Error Prone runs its default checks on every module at ERROR
with no baseline. NullAway runs at ERROR in JSpecify mode on the `io.github.marmer` packages only: main, test and
end-to-end sources in that package tree. The end-to-end POJOs in `foo.bar` are not NullAway-checked. Generated code is
not checked and carries no
license header. The JDK 17 leg skips the profile.

| [[concepts-frozen-5x-suite]]Frozen 5.x suite (part of `Domain docs in sync`)
| The `endtoend-5x-compatibility` module is the one the 5.x promise was made with, frozen except for the owner-approved deviations (version references filtered by the consumer build, `RelocationPomTest` deleted with #159), with the tree hash as the guard; its parent and own
version (`@project.version@`) follow the project version, as a 5.x user's version bump does. It is not a reactor module:
`endtoend-5x-compatibility-runner` builds it as a consumer build with the invoker plugin against an isolated local
repository that holds the reactor artifacts, so Maven resolves the bridge jars like it does for a 5.x user, with the project's own compiler plugin version. The suite runs every test it has; its `RelocationPomTest`, which asserted the former relocation POMs, was deleted with the owner's approval (#159), and each bridge module tests its own shape (`BridgeJarIT`). Its tree
hash must equal the stored one. Only the owner may update that hash.

| Ruleset against job names (part of `Domain docs in sync`)
| Every status check that the `main` ruleset requires is the name of an existing CI job, so a removed job cannot
block all merges.

| Docs sync (`Domain docs in sync`)
| The agent-facing glossary and ADRs are mirrored in these chapters, the required checks named in the agent docs are
CI job names, and the file names and packages that `CLAUDE.md` mentions exist.
|===

[[concepts-diagnostics]]
=== Diagnostics

The core reports a misconfiguration as a compiler diagnostic at the annotation that configured the type, once per
problem and naming the offending value (the unresolvable names of #113). A backend that finds a problem in a configured
type reports it the same way through `GenerationContext.reportError(message)`: the core prints the message as a compiler
error at the `@GenerateMatchers` annotation. The backend leaves the offending member out of its generated code, so the
error is the only one the user sees. The AssertJ backend does this for a generated method whose name an inherited
AssertJ method already has: one error per property, naming the property and the clashing methods. It also reports two
properties that generate the same method name (such as a boolean `foo` and `notFoo`, both `isNotFoo()`) and two nested
types whose factory constants share a name (such as `FooBar` and `Foo_Bar`, both `FOO_BAR`), one error per name. It
also reports a top level class name that two types of one package need (`Foo` and `AbstractFoo` both generate
`AbstractFooAssert`, or a type named like the package's mixin `SoftAssertionsProvider`) and then writes nothing for
the package, while `FooBar`, `Foo_Bar` and `FOOBAR` are different classes and no clash; like the other per-package
files it sees only the types of one processing round (<<adr-0006,ADR 0006>>).

A backend that leaves something out of its generated code without failing the build reports it through
`GenerationContext.reportWarning(message)`: the core prints the message as a compiler warning at the same annotation. The
Kotlin DSL backend uses it for a property whose name clashes with a member of its DSL scope; that property is left out of
the DSL and the Java matcher keeps it.
