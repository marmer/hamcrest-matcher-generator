[[section-solution-strategy]]
== Solution Strategy

The solution rests on a few fundamental decisions. The table connects each quality goal of <<section-introduction-and-goals,chapter 1>> with the
approach that serves it and with the place in this documentation where the approach is described.

[options="header",cols="2,5,2"]
|===
| Goal | Approach | Details

| Correctness
| Generated code is checked at three levels. Golden-file tests compare the generated sources character for character,
the end-to-end modules apply the processor to real beans and records and use the generated assertions in ordinary tests,
and a JaCoCo floor and PIT mutation testing guard the tests themselves. The generated code is plain Java or Kotlin that
the compiler checks, so a wrong property name is a compile error, not a test failure.
| <<concepts-ci-gates,chapter 8>> (CI gates), <<section-quality-scenarios,chapter 10>>

| [[strategy-non-intrusiveness]]Non-intrusiveness
| The configuration annotation sits on a separate configuration class, so configured types stay untouched and no runtime
dependency reaches production code. Both configuration annotations, `@GenerateMatchers` and the deprecated 5.x alias
`@MatcherConfiguration`, have `SOURCE` retention: the processor reads them from the source elements of the running
compilation, so a configuration class leaves no trace of them in its class file, even in the production sources.
| <<section-context-and-scope,chapter 3>>, <<section-runtime-view,chapter 6>>

| Usability
| The generated API is fluent and follows one naming scheme: `isX()`, `withFoo(...)`, `resetFoo()`, `ignoringFoo()` and
the opt-in completeness check. Mismatch messages name the property path of every failing check, and compile errors
point at the annotation and name the cause.
| <<runtime-mismatch-hamcrest,Describing a Mismatch (Hamcrest)>>: mismatch messages; <<concepts-diagnostics,chapter 8>>: diagnostics

| Build-tool agnosticism
| The processor uses only the standard annotation processing API of `javax.annotation.processing`. It runs under javac
for Java and under KAPT for Kotlin, in Maven and Gradle builds alike, and does not depend on a build plugin.
| <<context-technical-context,chapter 3>> (technical context), <<adr-0004,ADR 0004>>

| Maintainability
| One library-agnostic core builds a property model of each type. Every assertion library is a backend behind a small
interface (`GeneratorBackend`) that is found with `ServiceLoader`, so a new library needs a new module and no change of
the core. The dependency rules between the backends are stated in <<building-block-important-interfaces,chapter 5>>.
| <<section-building-block-view,chapter 5>>, <<adr-0001,ADR 0001>>, <<adr-0004,ADR 0004>>
|===

Further decisions that shape the whole system:

* *Generate code instead of reflecting.* Assertions are generated while the project compiles, with JavaPoet for Java and
KotlinPoet for Kotlin, and the IDE can navigate and complete the generated classes. The generated Hamcrest matchers pass
every property of their configured type to the runtime with a lambda that calls its accessor, and the AssertJ
assertions call the accessors directly, so a property of a configured type is read through its accessor, not looked up by
name. Reflection by name remains in exactly three places, and nowhere else:

* the Hamcrest runtime reads the properties of a value that is not an instance of the matched type, which the matcher
checks first;
* the Hamcrest runtime reads a property that was given no accessor: matchers generated by an older version pass only the
names, and matchers built by hand may do the same;
* the mismatch messages print the values of a configured type by its property names when the first matcher of that type
was generated by an older version, because it passed only names. Otherwise printing reads through the accessors.
* *Stay compatible with 5.x.* Tests written against 5.x keep compiling after a version bump; the rules are in
<<section-architecture-constraints,chapter 2>> and the decision in <<adr-0002,ADR 0002>>.
* *Keep the baseline modern, and the project maintainable without effort.* The Java 17 baseline
(<<section-architecture-constraints,chapter 2>>, <<adr-0005,ADR 0005>>) keeps dependency updates by Renovate from being
blocked by an old Java version. Releases are cut by release-please and
published from CI (<<section-deployment-view,chapter 7>>). After 6.0.0 no features are planned, only fixes and updates.
* *Document as code.* This documentation and the user guide are built with the project. Code in the guide comes from
example modules that compile and run in the same build, and the diagrams are views of one Structurizr model (<<adr-0003,ADR 0003>>).
