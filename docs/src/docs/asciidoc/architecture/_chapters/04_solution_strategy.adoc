[[section-solution-strategy]]
== Solution Strategy

The solution rests on a few fundamental decisions. The table connects each quality goal of chapter 1 with the
approach that serves it and with the place in this documentation where the approach is described.

[options="header",cols="2,5,2"]
|===
| Goal | Approach | Details

| Correctness
| Generated code is checked at three levels. Golden-file tests compare the generated sources character for character,
the end-to-end modules apply the processor to real beans and records and use the generated assertions in ordinary tests,
and a JaCoCo floor and PIT mutation testing guard the tests themselves. The generated code is plain Java or Kotlin that
the compiler checks, so a wrong property name is a compile error, not a test failure.
| Chapter 8 (CI gates), chapter 10

| Non-intrusiveness
| The configuration annotation has `SOURCE` retention and sits on a separate configuration class, so model classes stay
untouched and no runtime dependency reaches production code.
| Chapter 3, chapter 6

| Usability
| The generated API is fluent and follows one naming scheme: `isX()`, `withFoo(...)`, `resetFoo()`, `ignoringFoo()` and
the opt-in completeness check. Mismatch messages name the property path of every failing check, and compile errors
point at the annotation and name the cause.
| Chapter 6 (mismatch messages), chapter 8 (diagnostics)

| Build-tool agnosticism
| The processor uses only the standard annotation processing API of `javax.annotation.processing`. It runs under javac
for Java and under KAPT for Kotlin, in Maven and Gradle builds alike, and does not depend on a build plugin.
| Chapter 3 (technical context), ADR 0004

| Maintainability
| One library-independent core builds a property model of each type. Every assertion library is a backend behind a small
interface (`GeneratorBackend`) that is found with `ServiceLoader`, so a new library needs a new module and no change of
the core. Maven Enforcer and ArchUnit keep the dependency direction from drifting.
| Chapter 5, ADR 0001, ADR 0004
|===

Further decisions that shape the whole system:

* *Generate code instead of reflecting.* Assertions are generated while the project compiles, with JavaPoet for Java and
KotlinPoet for Kotlin. Nothing is looked up by name at test time, and the IDE can navigate and complete the generated
classes.
* *Stay compatible with 5.x.* Tests written against 5.x keep compiling after a version bump. Class names and the
`isX()`/`withFoo`/`resetFoo` API are kept, the old annotation stays as a deprecated alias and bridge jars cover the old
artifact names (ADR 0002).
* *Keep the baseline modern, and the project maintainable without effort.* The baseline is Java 17 (ADR 0005), so that
dependency updates by Renovate are not blocked by an old Java version. Releases are cut by release-please and
published from CI (chapter 7). After 6.0.0 no features are planned, only fixes and updates.
* *Document as code.* This documentation and the user guide are built with the project. Code in the guide comes from
example modules that compile and run in the same build, and the diagrams are views of one Structurizr model (ADR 0003).
