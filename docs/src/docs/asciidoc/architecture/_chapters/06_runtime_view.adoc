== Runtime View

=== Generation of matchers

The compiler runs the processor in every round in which it finds `@GenerateMatchers` or its 5.x alias `@MatcherConfiguration`. For every configured type
the following happens:

. `MatcherGenerationProcessor` hands the round to `MatcherGenerationProcessorWorker`, which resolves the configured class
and package names to types. Names that match nothing are a compiler error for `@GenerateMatchers` and a warning for the
5.x alias, which keeps 5.x configurations compiling. The `exclude` entries then leave out the configured types they name
by class or package, and the public member types they name are not modelled as nested types. An `exclude` entry that
matches neither a configured type nor one of their public member types is a warning. Types that carry the processor's
own `@Generated` marker are skipped with a note.
. `TypeModelFactory` creates the `TypeModel` of the type, including its public nested types. A configured type without
properties produces a compiler warning when the configuration names it; a type that only a package entry picks up gets
a verbose note instead, since packages hold types that are no match target. Each skipped method is reported with its reason, but only when the processor option
`matchergenerator.verbose` is given; without it the compiler prints no notes.
. The worker calls every `GeneratorBackend` found through `ServiceLoader` with that model and a `GenerationContext` (generator name, generation time, whether JSpecify is on the class path, the models of all types generated in the run, the inherited method names of a class on the compile class path, the error reporting `reportError`, whether KAPT's Kotlin output directory is there and the note reporting `reportNote`). The worker models every configured type of the round first and generates afterwards, so a backend knows the types of other configurations too.
There is no selection: the backends on the processor path are the user's choice.
. Each backend returns its `GeneratedSource` files, one per generated class. The AssertJ backend also returns one
`SoftAssertionsProvider` mixin per target package, from the first type of that package by name (see the glossary
entry *Soft assertions mixin*), and the same type writes the `PropertyRepresentation` of that package (see the glossary
entry *Generated representation*). The worker writes Java sources through the compiler's `Filer`, so they are compiled
in the same build.
. Kotlin sources are written into the directory named by the processor option `kapt.kotlin.generated`, which only KAPT
provides (see ADR 0004). The `GenerationContext` tells the backends whether that option is there. The Kotlin DSL backend
generates nothing without it and reports one compiler note, once per compilation; a backend that returns Kotlin anyway
makes the worker report one compile error that names the backend and the type, because the Kotlin file would otherwise
never be compiled.

A round without configuration can still reach the processor: the matchers written in an earlier round come back carrying `javax.annotation.processing.Generated` and `org.jspecify.annotations.NullMarked`. The processor claims these two annotation types in that round, and returns without generating anything. Without the claim, javac's `-Xlint:all -Werror` builds would fail on annotations nobody claims. The side effect is that javac skips a later processor in that round when that processor supports exactly these annotation types and nothing else.

Notable aspects::

* The model is built once per type and shared by all backends, so detection rules such as record components or
getter naming exist only once.
* A backend problem shows up as a compile error of the user's build, not as a failure of the user's tests. A backend
reports it through `GenerationContext.reportError`, once per problem, at the annotation (see chapter 8, Diagnostics).

=== Describing a mismatch (Hamcrest)

When an assertion with a generated Hamcrest matcher fails, the generated `<Type>Matcher` delegates `describeTo` and
`describeMismatchSafely` to its `BeanPropertyMatcher`, which builds the message in this order:

. It reads every checked property of the actual object and collects the failing checks as `path: expected ... but ...`
lines. A check that holds a generated matcher (recognised through `GeneratedBeanMatcher`) and meets an object of the
matched type recurses into it with the extended property path (`customer.address.city`). If the object is missing
(`null`) or of another type, the whole nested expectation is one failure.
. A check that holds any other matcher is a foreign check: the runtime asks that matcher whether it matches and for its
description and mismatch. Around these calls a per-thread depth counter is raised.
. A generated matcher that Hamcrest's own matchers (`contains`, `hasItem`, `hasEntry`) call while that counter is above
zero renders on one line (`OrderLine {sku "X-9", quantity <3>}`); otherwise it renders as a block (`Order with 4 property
checks`, one failing check per line).
. Values are printed by a `Description` that shows values of generated types from their properties, never via
`toString()`.

Notable aspects::

* The counter is raised only by generated matchers. A generated matcher that a foreign matcher holds directly, as in
`assertThat(list, contains(isOrderLine()))`, keeps the block format, because nothing generated has called the foreign
matcher.
* The properties printed for a type are the ones the first generated matcher of that type reported; properties every
object has (`class`) are left out.
