[[section-glossary]]
== Glossary

[cols="e,2e" options="header"]
|Generated code
|The source files that the processor writes into the user's project at compile time: matchers, assertions and Kotlin DSL files. They belong to the user and are not covered by the project's license.

|Runtime library
|The published artifact that generated code calls while the user's tests run, such as the Hamcrest `BeanPropertyMatcher`. Like every other artifact of the project, it is under the project's license (Apache-2.0).

|===
|Term |Definition

|Property model
|The description of a configured type and its properties that does not depend on any assertion library. All backends share it. In code it consists of `TypeModel` (a whole type with its nested types), `PropertyModel` (one property) and `TypeModel.Kind` (whether the type is a plain `POJO` or a `RECORD`).

|Nullability
|Whether a property may be `null`: `NULLABLE`, `NON_NULL` or `UNSPECIFIED`. The core derives it from the accessor: primitives are non null, JSpecify and JetBrains (Kotlin) annotations decide explicitly, and otherwise the closest `@NullMarked` or `@NullUnmarked` scope does. A type variable stays `UNSPECIFIED`. Generated Hamcrest code is `@NullMarked` with `@Nullable` on equality values and nullable property types, only when JSpecify resolves at compile time. Kotlin reports mismatches as errors; `-Xjspecify-annotations=warn` lowers them to warnings.

|Property
|A readable value of a bean (via its getter) or a record (via its component accessor) that generated assertions can check. Every generated matcher also has `class` (from `getClass()`) as a property, so `withClass(...)` and `ignoringClass()` are generated, as in 5.x, but the completeness check does not count `class`. Enums also get `declaringClass`; whether the completeness check should count it is still undecided.

|Backend
|A generator that turns the property model into assertion code for one specific assertion library, such as Hamcrest or AssertJ.

|Assertion class
|The pair of classes the AssertJ backend generates per configured type: `AbstractXAssert<SELF, ACTUAL>` on `AbstractObjectAssert`, which holds the generated assertions, and the concrete, non-final `XAssert` with a public `XAssert(X)` constructor and a static `assertThat(X)`. Neither is named `Assertions` or `SoftAssertions`, and none extends `org.assertj.core.api.Assertions`, so `assertThat(String)` stays unambiguous.

|Soft assertions mixin
|The interface the AssertJ backend generates per target package, named `SoftAssertionsProvider`, with a default `assertThat(X)` and a default `then(X)` for every generated type of the package. Mixed into a `SoftAssertions` or `BDDSoftAssertions` subclass, it makes the generated assertions soft and BDD assertions. The mixin covers only types generated in the same processing round; a type from another round or compilation is not in it.

|Generated representation
|The class the AssertJ backend generates per target package, named `PropertyRepresentation`: an AssertJ `StandardRepresentation` that prints an instance of each configured type by its properties, such as `Line[sku="A-1", quantity=2]`, nested types included, and formats every other value as AssertJ does. The user registers it with `Assertions.useRepresentation`; it is never registered automatically. Like the mixin, it covers only types generated in the same processing round.

|Bridge jar
|The code-free jar that a 5.x artifact (`hamcrest-matcher-generator-dependencies`, `hamcrest-matcher-generator-annotationprocessor`) is published as in 6.0.0. It depends on `hamcrest-matcher-generator`, so old coordinates still resolve to a jar and the Hamcrest backend arrives transitively. A relocation POM is not used because older compiler plugins do not follow it in a processor path.

|Configuration
|The single annotation-based declaration of the types for which assertions are generated. It is the same for every backend.

|Reference object
|An instance of a configured type whose property values are used as the expected values for all of its properties, so that a whole object can be compared in one step with `isXLike(reference)`. The comparison is deep for properties whose type has a generated matcher (also in lists, other collections, arrays and maps) and uses `equals` for the rest, including enums and types without properties. It turns the completeness check on, `withFoo`, `resetFoo` and `ignoringFoo` override single properties, and a cyclic object graph ends because a pair met again counts as equal. Deep comparison applies only to types whose matcher is generated in the same processing round; a type from another round or compilation is compared by `equals`. A back-reference to the root reference object shares the root's matcher, so an override on the root applies there too.

|Property path
|The route from the asserted object to the value that was checked, written with dots between property names, `[index]` for list items and `[key]` for map entries. Hamcrest mismatch messages use it to say exactly which value differs, for example `customer.address.city` or `lines[1].quantity`.

|Assertion path
|The AssertJ counterpart of the property path: the path of an AssertJ failure, rooted at the asserted type (`Order.customer.address.city`). The generated assertion of the value a `hasFooSatisfying` requirement is run for continues the path of the enclosing property, carried by the runtime class `AssertionPath`; an assertion for any other object created inside the requirement (`OrderAssert.assertThat(other)`) starts at its own type, because the path is bound to the value, not to everything created in the lambda. Inside an array, collection or map the path restarts at the element type (`OrderLine.sku`). Navigation with `extracting(.., as(X))` or `first(as(X))` starts a new path at the navigated type (`Customer.name`), while `hasFooSatisfying` keeps the root path (`Order.customer.name`). A missing asserted object reads `Expecting Order.customer not to be null`.

|Generated bean matcher
|A generated Hamcrest `<Type>Matcher`, identified at runtime by the interface `GeneratedBeanMatcher`. When one is used as the check of a property of another, the runtime flattens it into property paths instead of treating it like a foreign matcher.

|Collection matcher
|A runtime matcher for a collection or map property, created by `itemsInOrder(...)`, `itemsInAnyOrder(...)` or `entries(...)` in `CollectionMatchers`. Mismatches name the size, the path of every failing item or entry, and missing, closest and unexpected items or keys. Arrays count as lists. With the completeness check, `itemsInAnyOrder(...)` assigns items by their value checks and reports the properties neither checked nor ignored of an assigned item with its position, as in `contacts[1].phone`.

|One-line rendering
|The form in which a generated matcher describes itself and its mismatch, `OrderLine {sku "X-9", quantity <3>}`, while it is held by one of Hamcrest's own matchers such as `contains(...)`. Outside such matchers it renders as a block with one failing check per line.

|Completeness check
|The check that every property of a type is either checked or consciously ignored. It makes sure that a property added later cannot go unchecked without anyone noticing. Opt-in per assertion. A property counts as addressed by a check (`withFoo` in Hamcrest, `hasFoo`, `hasFooSatisfying`, `isFoo`, `isNotFoo` in AssertJ) or by `ignoringFoo()`, which both backends generate. Hamcrest runs the check with `checkingAllProperties()`; AssertJ runs it with the scope `satisfiesCheckingAllProperties(..)` or the closing call `hasAllPropertiesChecked()`. The scope form counts only the calls its requirements make, while the closing call counts the whole chain. Value mismatches fail first, and the check then names the properties that are neither checked nor ignored. Navigation with `extracting(.., as(X))` or `first(as(X))` yields a new assertion for a new subject, which has its own set of addressed properties: checks made before the navigation do not count for it, and a `hasAllPropertiesChecked()` after the navigation covers only the navigated type.

|DSL scope
|The Kotlin receiver block for one configured type (`isOrder { … }`), in which only that type's property checks can be written; a property of another configured type opens a nested DSL scope (`customer { … }`). Its class and entry function are named by the Kotlin DSL naming rule in arc42 chapter 5 (building block view).

|Generated code
|The source files that the processor writes into the user's project at compile time: matchers, assertions and Kotlin DSL files. They belong to the user and are not covered by the project's license.

|Runtime library
|The published artifact that generated code calls while the user's tests run, such as the Hamcrest `BeanPropertyMatcher`. Like every other artifact of the project, it is under the project's license (Apache-2.0).

|===
