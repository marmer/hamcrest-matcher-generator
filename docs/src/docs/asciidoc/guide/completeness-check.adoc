= Completeness check
:description: The completeness check fails a test when a property of a generated matcher or assertion was neither checked nor ignored, with the Hamcrest and AssertJ calls and the Kotlin DSL.
:page-order: 5

A test that checks some properties of a model says nothing about the others. When a property is added to the model later, the existing test passes and the new property stays unasserted. The completeness check closes that gap: when you turn it on, the assertion fails unless every property of the type is either checked or ignored.

A property counts as addressed when a check names it, or when you name it with `ignoringX()` to say that you decided not to check it. Ignoring is visible in the test, so the decision is reviewed with the test.

The check is off by default. It is opt-in per assertion, so a test that does not ask for it keeps the behaviour of 5.x.

The message is the last thing that fails. Value mismatches come first, so a wrong value is reported as a wrong value, and the check names only the properties that remain.

A matcher made with `isCustomerLike(reference)` turns the check on as well. The reference object sets every property, and `withX`, `resetX` and `ignoringX` override single properties of it.

== AssertJ

The AssertJ backend has two forms. The closing call `hasAllPropertiesChecked()` checks the whole chain of the assertion. Each `hasX`, `hasXSatisfying` and boolean `isX` or `isNotX` counts as a check, and `ignoringX()` counts as ignoring:

----

The scope form `satisfiesCheckingAllProperties(..)` runs the check only inside its lambda. It counts what the lambda addresses and nothing that comes before it in the chain. Use it when only one part of a larger assertion should be complete:

[source,java]
----
include::../../../../../example-maven-java-assertj/src/test/java/example/assertj/CustomerAssertTest.java[tag=completeness-check-scope,indent=0]
----

A failure names the properties in a sentence of this form: `Expecting every property of Order to be checked or ignored, but these were neither: tags`. The check of a nested assertion names the path of the nested type, so the same sentence for the `customer` of an order starts with `Order.customer`. This sentence is the one the AssertJ end-to-end test `CompletenessCheckTest` asserts.

Navigation with `extracting(..., as(X))` or `first(as(X))` starts a new assertion for a new subject. That assertion has its own set of addressed properties, so checks made before the navigation do not count for it.

== Which properties count

Every generated matcher also lists `class`, from `getClass()`, so `withClass(..)` and `ignoringClass()` exist. The completeness check does not count `class`: you never need to ignore it. Enum types also get `declaringClass`, and whether the check should count it is still open.
