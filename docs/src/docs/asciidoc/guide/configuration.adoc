= Configuration
:description: Choose the types to generate for with the configuration annotation, exclude types and set the package of the generated code.
:page-order: 2

One annotation, `GenerateMatchers`, tells the processor which types to generate for. Put it on a class of your choice. The backends on the processor path both read it, so a configuration selects the same types for the Hamcrest matchers and the AssertJ assertions. The annotation has source retention: the processor reads it while compiling, and the compiled class of your configuration class carries no trace of it.

== Selecting types

The annotation's value lists package names and fully qualified class names. A package entry selects every class in the package, and a class entry selects exactly that class:

[source,java]
----
include::../../../../../example-maven-java-hamcrest/src/test/java/example/hamcrest/configuration/HamcrestConfiguration.java[tag=configuration,indent=0]
----

This configuration generates a matcher for every model class in `example.hamcrest.model`. The model classes can be beans with getters, records or Kotlin classes: the processor reads bean getters, record component accessors and Kotlin getters. A getter that declares a checked exception is still a property: a check of it fails with `Could not read property 'name'` and the exception as cause.

Lombok-generated getters are read as well, provided the Lombok annotation processor runs before the generator. Put Lombok first on the processor path, as the Lombok end-to-end module `hamcrest-matcher-generator-endtoend-lombok` does, so that the generator sees the getters Lombok adds in the same compilation. That module is tested with the Lombok version of the project's root pom.

== Excluding types

The annotation's `exclude` value takes the same kinds of entries and removes types from the selection. A package entry excludes every configured type in it, and a class entry excludes that one type. An entry that matches no configured type is reported as a warning, so a misspelled name does not pass silently.

== Package of the generated types

The generation setting `packageConfig` decides the package of the generated types. Its value is a prefix, so the generated code of a type can live in a package other than the one of the type. The javadoc of the annotation gives the rule with examples: the prefix `some.praefix.` turns the package `some.pck` of `some.pck.SomeType` into `some.praefix.some.pck`, and an empty value keeps the package of the type. A type that is not public keeps its own package: when a prefix would move it, a package entry skips the type, and naming the type in the configuration is a compiler error.

== Where the generated code goes

With Maven, the generated sources of a configuration in `src/main/java` go to `target/generated-sources/annotations`, and those of a configuration in `src/test/java` go to `target/generated-test-sources/test-annotations`. The example modules keep their configuration in `src/test/java`, so their matchers are generated into the test output only, and the production artifact contains neither them nor the configuration. A configuration in `src/main/java` is the special case: its matchers join the production code, so the generator needs the `provided` scope with `<optional>true</optional>`, as the link:getting-started.html[getting started chapter] describes.

== Using both backends for different types

Every backend on the processor path generates for every configured type. A configuration that has the Hamcrest and the AssertJ artifact on the processor path therefore gets a matcher and an assertion for each of its types. To generate Hamcrest matchers for some types and AssertJ assertions for others, put the configurations in separate modules, or in separate compiler executions that each have their own processor path and name only the backend they need.
