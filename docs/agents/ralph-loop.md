# Ralph loop (`goRalph`)

The skill is called `goRalph`. A script-driven loop for long unattended implementation runs in a cloud session. The main session only starts the script and watches its status; the work happens in fresh `claude -p` processes. Research and measurements: `docs/research/ralph-loop-in-cloud-sessions.md`. Spec #410; what is built (#411 to #420; #417 is a process ticket, the rules in `implementation.md`) and what is still planned (the open ticket #422; the trial #421 is done) are separated below.

## Terms

**Run**:
One start of the loop script until it ends: the frontier is empty, a limit is reached, or a stop was requested.
_Avoid_: session (that is the Claude Code session the main session runs in)

**Iteration** (German: Runde):
One fresh orchestrator process started by the script with the same prompt. It reads the state from the issue tracker, Git and the run directory, does its work and ends; the next iteration starts with an empty context.

**Work step** (German: Arbeitsschritt):
The smallest unit after which the state is saved by commit and push, e.g. "ticket implemented", "review round 2 fixed", "PR opened". A stop `after-step` waits for the current work step to end.

**Control file**:
`control.json` in the run directory. It holds the limits (`until`, `max_duration`, `max_iterations`, `max_iteration_duration`, `max_parallel`), the stop kind a reached limit acts as (`limit_stop`, default `after-step`) and the stop request `stop` (`now`, `after-step`, `after-iteration`; `true` means `after-step`). `until` is `YYYY-MM-DD HH:MM`, optionally followed by a zone name (Europe/Berlin otherwise); durations are whole minutes. The script validates every value (`ERROR` line, exit 2) and reads the file before each iteration, a stop `now` and `max_iteration_duration` also while the iteration runs (every 5 s; kill after a grace period of 5 min); the orchestrator reads it between work steps; changing it changes the running loop.

## Monitor lines and status file (reference)

The one place that lists what the script prints and writes; `SKILL.md` and the other docs point here. Stdout carries one line per iteration end, retro end, error, denial, stop, usage limit wait and run end, nothing else:

| line | meaning |
|---|---|
| `iteration <i> ok: <n> turns, cost $<usd>`, with `, tickets <#n ...>, PRs <#n ...>` appended (`none` for an empty list) when the iteration wrote its work data | the iteration ended with a result; the suffix comes from the work data file (#439, below), without a valid file the line has no suffix |
| `retro iteration ok: <n> turns, cost $<usd>`, `ERROR retro failed: <reason>` (reasons as for an iteration) and `DENIAL retro: [...]` | the retro iteration (#418, below); it is no iteration of the run, so it is not in the counts of the `END` line, and a failed retro does not change the end of the run; `STOP retro killed (<reason>)` (#438) is a retro killed by the watcher, reasons as for `STOP iteration` |
| `ERROR iteration <i> failed: <reason>` | a real failure; reason is `no result event (exit <rc>)`, `unreadable result event (exit <rc>)`, `exit <rc>, <subtype>`, `is_error set, <subtype>` or `no result field, <subtype>` (e.g. a turn limit) |
| `ERROR frontier check for #<spec> failed: <stderr>` and `ERROR PR check for #<spec> failed: <stderr>` | the work check failed (never read as green); an `END` line follows |
| `WAIT usage limit hit in iteration <i>: no claude process until the retry in <s> s (waited <w> of <cap> s)` and `WAIT over, retrying (waited <w> of <cap> s)` (or `WAIT over, stop requested or limit reached ...`) | the iteration ended on the usage limit: a result event with `is_error` that has `api_error_status` 429 or a text with "hit your limit" or "usage limit", whatever the exit code; the iteration counts as neither `ok` nor `failed` and not as an iteration, the script starts no `claude` process during the wait and runs the iteration again afterwards (see below) |
| `DENIAL iteration <i>: ["<tool>", ...]` | `permission_denials` of the result |
| `STOP iteration <i> killed (<reason>)` | a deliberate stop, not a failure: `stop now`, or `max_iteration_duration <n> reached and grace period over`; it counts in `failed` of the run |
| `END after <i> iterations: <reason> (<ok> ok, <failed> failed)` | the run ended: `stop requested (<kind>)`, `until ... reached`, `max_duration <n> reached`, `max_iterations <n> reached`, `usage limit not lifted within <cap> s`, `no ticket ready for an agent`, `frontier check failed` or `PR check failed` |

Usage limit wait (#414): the pause is `RALPH_LIMIT_RETRY_SECONDS` (default 600), sliced by `RALPH_POLL_SECONDS` so that a stop request or a reached limit ends it early. The waits add up to at most `RALPH_LIMIT_CAP_SECONDS` (default 5 h 15 min = 18900 s); the sum starts again at zero after an iteration that no usage limit cut off. When the cap is used up and the limit is still there, the run ends with `END ... usage limit not lifted within <cap> s`. The script does not read the reset time from the message, it retries at the pause; the result file of a cut-off iteration is kept as `limit-result-<i>-<epoch>.json`.

Work data (#439): before it ends, the orchestrator writes `iteration-<i>.json` into the run directory with `scripts/agents/ralph-iteration.py data` (below) as `{"tickets": [<numbers>], "prs": [<numbers>]}` (the bullet of `iteration-rules.md` that names it; `<i>` is the iteration number from the "This run" section of the prompt). After an ok iteration the script appends the tickets and PRs to the ok line. A missing or malformed file (anything but an object whose two keys are arrays of numbers from 1 on) leaves the line as it is without the suffix and adds no `ERROR` line. The script deletes the file of an earlier attempt before each iteration, so a retry after a usage limit never reads the data of the cut-off attempt. The source is a file, not the result text: the result text is the free prose of `/implement-spec`, and a file keeps the numbers exact. Tested by the `iteration_end_line`, `malformed_iteration_data`, `each_iteration` and `cut_off_by_the_usage_limit` tests of `test_go_ralph_loop.py`.

Exit codes:

- 0 after an `END`.
- 2 for a stale or offline start (#489): before the lock and the run directory, a new run and `--resume-only` fetch `origin main` and refuse when `HEAD` does not contain `origin/main` (`ERROR branch <name> is <n> commits behind origin/main, update it or start from main`) or the fetch fails (`ERROR fetching origin main failed in <repo>, the loop needs the network`); a branch on or ahead of `main` starts as before, and the check runs only at the start. Tests: `test_a_branch_behind_main_is_refused_without_run_directory_or_lock` and its neighbours in `test_go_ralph_loop.py`.
- 2 for a value the script cannot read (option, environment variable or a hand edit of the control file: `ERROR <what is wrong>`, the run stays unfinished) and for a missing tool (`jq`, `flock`, `mktemp`, `timeout`).
- 1 when the lock of the spec is held (`ERROR spec #<n> already has a running loop (pid <pid>), lock <path>`) and for the refusal of `--resume-only` (`ERROR no run of #<n> to resume`, `ERROR run of #<n> already ended, nothing to resume`).
- `interview.py` and `summary.py`: 1 for a failed or timed-out tracker call, 2 for a wrong argument or `RALPH_GH_TIMEOUT_SECONDS` (an integer of at least 1, as in `loop.sh`).
- `ralph-iteration.py` (#455): 0 done, 1 when the `gh` call of `auto-merge` failed, timed out or `gh` is missing (`ERROR auto-merge for #<n> failed: <reason>`), 2 for a wrong argument or `RALPH_GH_TIMEOUT_SECONDS` (`ERROR <what is wrong>`).
- 143 when the script itself is terminated.

`status.json` in the run directory is rewritten atomically (temp file, then `mv`) at every state change: `spec` (string), `state`, `iteration` (number of the current or last iteration), `ok`, `failed` (counts of the run, recovered after a restart) and `run_dir`. States: `running` (an iteration runs), `retro` (the retro iteration runs), `waiting` (PRs wait for CI or a usage limit has to lift, the script sleeps), `between` (after an iteration, before the next check) and `ended`.

## Built

- The loop works on one spec: its argument is the spec issue number, the frontier comes from `scripts/agents/issue-status.py`. The frontier skips a ticket with an open PR or a remote `ticket-<n>` branch (`Closes #n` fires only on merge, so such a ticket still looks free; #451): its PR is left to the work check below. A run ends by itself when the frontier holds only `ready-for-human` or `needs-info` tickets and no PR needs action or waits (#411, #413).
- Run state lives outside the repo in `~/.goRalph/runs/<spec>-<start time>/` (control, status, per-iteration results and streams); one active run per spec through a lock under `~/.goRalph/locks/`, and a new start for the same spec continues an unfinished run (#411).
- `/goRalph` takes its arguments in plain language (e.g. `/goRalph #312 bis 6 Uhr, max 7 Runden`); the main session turns them into options of the script and shows the parsed values in one line before starting. Defaults: no time, duration or iteration limit, `max_parallel` 3 (#412).
- No cost budget and, by default, no limit on how long a run or an iteration lasts. A reached limit acts as a stop request of the kind set in the control file, `after-step` unless stated otherwise; it acts within one poll slice also while the script sleeps for waiting PRs. `until` times are Europe/Berlin unless a zone is named (#412, #413).
- Usage limit wait: an iteration that ends on the usage limit is waited out and run again, at most 5 h 15 min (#414; details under the monitor lines). The cap is summed per stretch of consecutive limit hits, reset by any iteration the limit did not cut off; that reading of "in total" is an assumption the owner must confirm.
- Stop kinds stay three: `after-iteration`, `after-step` (the default, also for a stop request without a kind) and `now`; there is no interrupt-and-save mode. `stop: now` terminates the child process group; the state is the last pushed work step, uncommitted changes are lost (no automatic WIP commit) (#412).
- Iteration prompt: the script calls `claude -p "/implement-spec <spec>"` with `--append-system-prompt` from `.claude/skills/goRalph/scripts/iteration-rules.md`, which holds only the loop rules (control file, `max_parallel`, handover note, owner question as ticket comment plus `needs-info`, PRs with squash auto-merge, one CI wait, one CI fix, the work data file of the ok line (#439), and a pointer to the escalation rule), tested by `IterationRulesTest`. `/implement-spec` with `implementation.md` stays the only description of how a ticket is implemented. Review chain, escalation path (orchestrator `sonnet`, no `opus` in the loop) and parallel tickets are rules of `docs/agents/implementation.md`, shared with hand-run sessions; `max_parallel` is a hard number the orchestrator reads from `control.json` at the start (Read tool on the literal run directory of "This run") and re-reads before each new implementer, after each implementer has reported, after each merge and before each review round, so at most that many implementers run at a time (#411, #417, #456).
- Background wait ceiling (#485): `claude -p` stops background subagents 10 minutes after its last turn (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, default 600000); `start_claude` in `loop.sh` gives every child (iteration and retro) `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=3600000` unless loop.sh's environment already sets it, and that value wins. It was 10 minutes in run 104, iteration 1, and stopped two implementers (their branches were pushed without PRs). One hour, not `0`: `0` waits indefinitely, and then no limit of the iteration is left except `max_iteration_duration`, which is absent by default. Pinned by four tests in `scripts/agents/test_go_ralph_loop.py` (default and already-set, iteration and retro).
- Child permissions (widened in #473; the owner approved the widening in that ticket, because the narrow list made the trial children waste turns on denied `cat`, `ls`, `;` chains, `$VAR` and pipes): `--allowedTools` is `Bash,Read,Edit,Write,Agent,Skill`, so every Bash command is allowed (no enumerated prefixes, which also ends the `python3 scripts/*` and `head`/`grep` pipe workarounds of #466), plus `permissions.deny` in `--settings` and `disableAllHooks`; no `bypassPermissions`; `WebFetch` and `WebSearch` are not allowed (the child has `gh api`, and `curl` is allowed through Bash; no probe showed a need). A deny rule overrides an allow rule, and a pattern is a glob with `*` (matched against the command text; a pipeline or chain is checked per command, and a pattern that spans a pipe, such as `curl*|*sh*`, was probed, see the table in the comment on #473). A pattern ending in `:*` is read as the legacy prefix form with a word boundary (#466) and matched nothing for `git push* :*`; `git push* :**` works (probed), and a test pins that no pattern ends in `:*`. Denied, and what each entry stops:
  - the old entries, unchanged: `git push --force*`, `git push -f*`, `git push origin main*`, `git push origin HEAD:main*`, `git reset --hard*`, `git branch -D*`, the hand merge routes of #457 (`gh api` with `-X`, `-XPUT`-style or `--method` / `--method=` set to `PUT`, `put` or `Put` in any flag order, `mergePullRequest`, `gh pr merge`);
  - history and `main` (new): `git push` with `--force` (also `--force-with-lease`, `--force-if-includes`) or `-f` anywhere; with `main` as a whole word or refspec part (`origin main`, `HEAD:main`, `HEAD:refs/heads/main`, `+main`, `:main`, `main:main`, `--delete main`; anchored, so `retro-domain-...` and `review-<n>-maintenance` are pushable); with `--delete`, `-d`, a `:<branch>` refspec (`git push* :**`) or `+<refspec>`; with `--mirror` or `--prune`. git accepts unambiguous long-option abbreviations, so the globs are the shortest unambiguous prefixes (checked against `git push --git-completion-helper`, git 2.43): `--de*` (`--d` is ambiguous with `--dry-run`), `--m*`, `--pru*` (`--pr` is ambiguous with `--progress`), and `--force*` (`--for` and `--forc` are ambiguous and git rejects them); `git reset` with `--hard` anywhere; `git branch` with `-D`, ` -f`, `--force`, `-df`, `-fd`, or `-d` / `--delete` naming `main`; `git update-ref` naming `main`; `gh api` with `DELETE`, `delete` or `Delete` after `-X`, `-XDELETE`-style, `--method` or `--method=` (so also deleting the repository itself or a branch ref), any `gh api` naming `git/refs/heads/main`, `branches/main` or `/merges` (the hand merge route `POST /merges`), `gh repo delete`, `archive`, `edit` and `rename`;
  - the machine: `rm` with a recursive flag (anything containing `r`) and the target `/`, `~`, `~/`, `$HOME`, `$HOME/`, `${HOME}`, `.`, `..`, `*.git` (also `.git`, `/x/.git`), `*.goRalph`, `*.goRalph/runs` (also with a trailing `/`); `sudo*`, `doas*`, `su`; `git config` naming `credential`, `--global` or `--system`; `git credential`; `curl` or `wget` piped into `*sh*` or `*python*` and `sh <(`, `bash <(`; `bash -c`, `sh -c`, `zsh -c` and `eval` (the probe showed that `bash -c 'git push origin :<branch>'` bypassed every other entry, since a pattern sees only the outer command text).
  - Branch deletion: `git branch -d <branch>` is allowed (refuses an unmerged branch; with squash merges a merged ticket branch counts as unmerged, so use the wrapper). `git push --delete` and `:<branch>` are denied, because the pattern language has no "except these names" (a deny rule overrides an allow rule), so the remote deletion is the wrapper command `python3 scripts/agents/ralph-iteration.py delete-branch <name>` (`ralph-iteration.py`): it accepts only `ticket-<n>`, `session-end-*`, `retro-*` and `review-*` and only a branch whose pull request is merged and none is open and whose local and remote tips both equal the `head.sha` of a merged pull request (a branch with later commits, or a name reused after a merge, is refused), asks `origin` first (an `ls-remote` exit code other than 0 or 2, for example 128 for a network or auth failure, is an `ERROR delete-branch` line and deletes nothing), deletes the local and then the remote branch, and refuses `main` and every other name with exit 2 (tests in `test_ralph_iteration.py`).
  - What is not covered (known gaps, the owner reads them): a pattern matches the command text, so anything that reaches the same effect without the text is not covered: `rm` through a script, `find -delete`, `git` or `gh` through a script or `python3 -c` (probed: `python3 -c` running `git push origin :<branch>` was not denied), `perl`, `node`, a heredoc, `xargs`, `env`, `command`, `nohup`, a flag order the globs do not list (`rm -rf -- /` is listed through `*r*`, `rm / -rf` is not), other mixes of case such as `pUt` and `dEleTe`; `rm -r` of any path but the listed ones (for example `/home`, `/etc`, the repository's working tree, another run directory); `chmod`, `dd`, `mkfs`; `gh api` PATCH or POST on the repository itself (archive, default branch, visibility) and the REST routes that rewrite other refs (`git/refs/heads/<other>`); a bare `git push` or `git push origin <branch>` with an upstream that points at `main` (the `main` glob sees only the text); `git checkout -B main` and `git switch -C main`; writes to files outside the repository (`~/.ssh`, `~/.gitconfig` through `tee`, `sed -i`), and reading or printing secrets (the rule "never expand secrets" in `iteration-rules.md` is a rule, not a block); the comment-body false positives of the substring globs (a comment containing `-X DELETE`, `git push` text with `main`, `/merges` is denied); `Edit` and `Write` stay unrestricted, so the child can edit the wrapper script, `loop.sh`'s rules files and the tests (the next run reads them); bundled short flags such as `git push -uf` and `-ud` (the `-f` and `-d` globs need a space before the dash and a single letter; the abbreviation fix does not cover short clusters); `git branch -d <any other local branch>` is allowed (local only; the remote deletion needs the wrapper); the read `gh api .../branches/main` is denied as a false positive of the `branches/main` glob. `curl`/`wget` themselves stay allowed.
  - the same lists serve the iterations and the retro; reads such as `gh api repos/<o>/<r>/pulls/<n>` stay allowed; the loop children use the wrapper for auto-merge, `docs/agents/wayfinding.md` is for hand-run sessions and names the MCP tool `enable_pr_auto_merge` (`gh pr merge --auto --squash` is the fallback there), which a loop child does not have; the loop denies `gh pr merge` because a deny rule cannot say "without `--auto`", and the wrapper uses the REST route instead; when the auto-merge fails (#450) the PR waits, rule in `iteration-rules.md`; denials become a `DENIAL` line.
  - Probe evidence: that `permissions.deny` holds in `-p` without hooks was verified for `git branch -D` and `git push --force` in trial #421 (`docs/research/ralph-loop-in-cloud-sessions.md`, section 9) and for the #473 entries by the probe table in the comment on #473 (haiku, `-p`, the real strings of `loop.sh`, nonexistent targets only, abbreviations `--del`, `--dele`, `--mirr`, `--m`, `--prun` included). Not probed for real, glob emulation in the tests only: `rm -rf /`, `rm -rf ~/`, `rm -rf $HOME/` and `rm -rf ${HOME}` (the model refused to issue those calls), and the `rm *r* ..`-style variants beyond the probed ones.
- Literal run values and the wrapper (#455): trial #421 showed that the child's Bash calls with `;`, `&&` or `$RALPH_RUN_DIR` are denied, so it never learned the run directory. `loop.sh` appends a section "This run" to the system prompt of every iteration (`Run directory: <path>`, `Iteration: <n>`) and of the retro (`Run directory: <path>`, `Last iteration of the run: <n>`), as literal values. `scripts/agents/ralph-iteration.py` covers the recurring steps with one allowed command each (the child reads `control.json` with the Read tool on the literal run directory): `data <run dir> <iteration> --tickets ... --prs ...` (writes `iteration-<i>.json`, validated) and `delete-branch <name>` (#473, below) and `auto-merge <pr>` (squash auto-merge through the REST route `PUT /repos/{owner}/{repo}/pulls/{n}/ccr/auto_merge` of cloud sessions, since GraphQL is blocked there; on failure an `ERROR` line and exit 1, never a merge). The rule "never merge by hand" stays in `iteration-rules.md` and the deny list blocks the hand routes (#457). Tests: `test_ralph_iteration.py`. Result of probing the route: research file, section 9.4. Unverified until the first real run (#422): the success case on a real PR and the `merge_method` field of the request (research file, section 9.4).
- PRs: an iteration opens the PRs of its tickets with squash auto-merge and waits for CI with one blocking poll (no tokens while blocked), at most 30 min. On red CI it fixes once itself while its context is fresh; anything left (second red run, merge conflict, timeout) goes to the next iteration through the ticket's handover note `notes/ticket-<n>.md` on the ticket branch, updated after every work step. The iteration ends when its PRs are merged or after that one CI fix (`iteration-rules.md`).
- Work check before each iteration (`loop.sh`, `check_prs`, #413): through `gh api`, without a model, free frontier tickets (not those with an open PR or a remote `ticket-<n>` branch) or PRs that need action (red CI, conflict, new review comment) start an iteration; only PRs waiting for CI with auto-merge make the script sleep and check again every 5 min; nothing at all ends the run. This is a separate mechanism from the iteration's blocking poll: it handles the PRs left over after an iteration ended (timeout, second red run, conflict, new review comment) and costs no tokens.
  - Which PRs: the open ones on branches `ticket-<n>` of the spec's sub-issues. Every list is read page by page (`per_page=100&page=1, 2, ...` over `repos/{owner}/{repo}/...` until a page has fewer than 100 items; `gh_pages` in `loop.sh`, `gh_list` in `ghapi.py`), never with `gh api --paginate`: its `Link` header leads to `repositories/{id}/...` paths, which the cloud proxy refuses with 403 (`docs/research/gh-paginate-proxy-403.md`). A list still full at `RALPH_GH_MAX_PAGES` (default 100) is an error naming the endpoint, never a truncated list. Every `gh` call has a timeout (`RALPH_GH_TIMEOUT_SECONDS`, default 60; `interview.py` and `summary.py` read the same variable through `ghapi.py`). A failed call, a timeout or an answer `jq` cannot read ends the run with `ERROR PR check ... failed`, never as green.
  - Needs action: a check run failed, the merge state is `dirty`, or a review comment (not a reply in a thread) or a review (changes requested, or with text) is newer than the head commit.
  - Waiting: no action needed, auto-merge is on, and CI is still pending (a check run not completed, or none yet). The pause is `RALPH_PR_SLEEP_SECONDS` (default 300), sliced by `RALPH_POLL_SECONDS` so that a stop request or a reached limit ends it early. A green PR that is blocked, behind or unstable with all checks completed is neither action nor waiting, so it cannot keep the script asleep forever.
  - A free frontier ticket wins over waiting PRs.
  - Known limit: "newer than the head commit" compares with the committer date, which the author controls, and the REST API has no push time; a comment on a commit with a future date is missed, one on a back-dated commit counts as new. Replies are ignored so that an iteration that only answers on a thread does not trigger itself again.
- Resume (#415): a start continues the unfinished run (no `ended` marker). Iteration number and the `ok`/`failed` counts are recovered from `result-<i>.json` and `outcome-<i>` (`ok` or `failed`, written per iteration); a result without an outcome counts as failed, so `ok + failed == iteration` after a resume. A finished run is never resumed: a plain start begins a new run, `--resume-only` (used by the check-in) refuses with an `ERROR` line and exit 1 when the spec has no unfinished run. The main session's safety net (monitor re-arm, hourly check-in with a status line and a restart through `--resume-only`) is described in the `goRalph` skill, step 7.
- Main session output: the monitor lines above; no live status page, `status.json` on request; at run end one summary page as an artifact from `scripts/summary.py` (duration, counts, merged PRs, escalations, open questions, new retro tickets; no cost) (#420).
- Retro iteration (#418): the last iteration of every run that ends with a stop `after-step` or `after-iteration`, a reached limit acting as one of those (`limit_stop` not `now`) or an empty frontier ("no ticket ready for an agent"); never after a stop `now` (also a limit acting as `now`), and not when the run ends on an error (`frontier check failed`, `PR check failed`) or on a usage limit that does not lift. The script calls `claude -p "/retro non-interactive <run dir>"` with the model, `--settings` and `--allowedTools` of the iterations and `--append-system-prompt` from `.claude/skills/goRalph/scripts/retro-rules.md` (the non-interactive mode) instead of the loop rules, before it writes the `END` line. Choices: it counts neither as an iteration nor as `ok`/`failed` (so `ok + failed == iteration` still holds after a resume), has its own monitor lines (above), own files `retro-stream.jsonl`, `retro-result.json`, `retro-stderr.txt` and the marker `retro-done` (a restart after a script death during the retro runs it again, after it finished it does not), and the watcher of an iteration (#438, below); a run that ended with zero iterations (e.g. an empty frontier at the start) still gets its retro.
  - Retro rules of #438 (chosen rules, owner to confirm; (d) too): (a) the retro has the same watcher as an iteration: a `stop now` written while it runs kills its process group, `max_iteration_duration` bounds it with the same grace period (it writes the limit's stop kind into the control file as for an iteration), and either gives one `STOP retro killed (<reason>)` line (no `retro iteration ok`/`ERROR retro failed` line then) followed by the `END` line of the run, whose reason stays the one that led to the retro. (b) A usage limit during the retro (result event as for #414) is not waited out: no retro, one line `ERROR retro failed: usage limit hit, no retro`, no `WAIT` lines and no second attempt, then `END`. (c) `until` and `max_duration` do not bound the retro: it runs after the run ended on them and only (a) bounds it. (d) A retro killed by the watcher (stop now or `max_iteration_duration`) or ended by a usage limit still counts as done: `retro-done` is touched, so a restart (resume) does not run it again. Pinned by the `test_*retro*` and `test_*_does_not_bound_the_retro` tests of `test_go_ralph_loop.py`.
  - Non-interactive `/retro` (`.claude/skills/goRalph/scripts/retro-rules.md`, not in the `retro` skill itself, which is a vendored skill under `.agents/skills/` that is never edited): it changes only lessons for implementers in `docs/agents/implementer-brief.md` and the learnings file, in its own branch `retro-<spec>-<date>` and PR with the usual review; everything that changes rules, model defaults, gates, prompts or the loop becomes a ticket with the labels `retro` and `ready-for-human` holding options and a recommendation. It creates the `retro` label itself when it is missing.
  - Learnings file `docs/agents/goRalph-learnings.md`: read by every iteration (the first rule of `iteration-rules.md`), at most 40 lines, pinned by `LearningsFileTest`. When full, the retro condenses it: general lessons move to the implementer brief, obsolete ones are deleted, and if it still does not fit, a retro ticket proposes raising the limit or restructuring. Whether 40 lines are enough is open.
- The request to run `/retro` at the end of a session is dropped for sessions that started `/goRalph`, because the loop is to run its own retro (#418); the rule is in `docs/agents/implementation.md` ("Retro at the end of every session"), `CLAUDE.md` and the `brief-me` skill (#417).
- Pre-run interview (#419, `goRalph` skill step 2): before the script starts, the main session asks `scripts/interview.py list <spec>` (no model, tested by `test_go_ralph_interview.py`) for the open `needs-info` tickets of the spec and the open retro tickets (`retro` and `ready-for-human`). With nothing open the interview is skipped and the run starts at once. Otherwise all items are presented in one round with options and a recommendation; each answer becomes a ticket comment and `ready-for-agent` replaces `needs-info`. A dropped retro ticket is closed as not planned with the reason. An accepted retro ticket is planned right away (acceptance criteria, `**Implementer model:**` line) and gets `ready-for-agent`, but it is deliberately NOT made a sub-issue of the spec: the loop's frontier (`issue-status.py --frontier`) reads only the sub-issues, so the starting run cannot take it (pinned by a black-box test in `test_go_ralph_loop.py`). The next start of a NEW run finds it as `carry_over` in the lister's output (labelled `retro` and `ready-for-agent`, no sub-issue of the spec) and attaches it with `interview.py attach <spec> <n>...` before its own interview, so that run takes it as frontier work. A call that continues an unfinished run attaches nothing: the lister reports `unfinished_run` (a run directory `runs/<spec>-*` without an `ended` marker, as `loop.sh` finds it), and the tickets wait for the next new run. The interview itself is skill text with no automated test; it is checked in the first real run. A retro ticket that already has a parent (`parent_issue_url`, e.g. a sub-issue of another spec) is not `carry_over`, and `attach` reports a ticket it cannot attach on stderr (exit 1) while still attaching the others.
