# Modules

The module list is the root `pom.xml` `<modules>`; this file gives the roles of the modules and the rules the poms do not state.

The published modules' roles: `matcher-generator-annotations` (`@GenerateMatchers` and the deprecated 5.x alias `@MatcherConfiguration`, the only type left in the old package), `matcher-generator-core` (property model, type discovery, diagnostics, `GeneratorBackend` SPI and the processor entry point; no Hamcrest/AssertJ, enforced by Enforcer `bannedDependencies` and an ArchUnit test), `hamcrest-matcher-generator` (the Hamcrest backend, registered via `ServiceLoader`, plus the `BeanPropertyMatcher` runtime library), `assertj-assertion-generator` (the AssertJ backend: `AbstractXAssert`/`XAssert` per type, plus the small `AssertionPath` runtime; depends only on core, enforced by Enforcer `bannedDependencies` and an ArchUnit test) and `hamcrest-matcher-generator-kotlin` (the opt-in Kotlin DSL backend: one `<Type>MatcherDsl` Kotlin file per type, delegating to the Hamcrest matcher, so it is the single backend-to-backend dependency, on the Hamcrest backend; ADR 0004). `hamcrest-matcher-generator-dependencies` and `hamcrest-matcher-generator-annotationprocessor` are bridge jars with no functionality for 5.x users: jar packaging, a dependency on `hamcrest-matcher-generator` at `${project.version}`, no relocation (ADR 0002; `BridgeJarIT` in each); the parent is `matcher-generator-parent`. Each published jar sets `Automatic-Module-Name` to its package root (`AutomaticModuleNameIT`). The `*-endtoend-*` modules form one reactor group through the aggregator `hamcrest-matcher-generator-endtoend/pom.xml` (their parent, `maven.deploy.skip`, and `-Xlint:all -Werror` for their compilation). A new published backend module needs: the root `<modules>`, `scripts/ci/check-release-artifacts.sh`, `.github/workflows/ci-build.yml` (the `mkdir` source-dir line, the Sonar `--projects` list and the PIT `--expect` list of the `Mutation testing` job), a `mutation` profile in its pom, the core Enforcer exclude list, `AutomaticModuleNameIT` and `LicenseFilesIT`, a `src/test/resources` directory for the golden IT, and for its end-to-end module the aggregator and the release `excludeArtifact` list. The exceptions are `hamcrest-matcher-generator-endtoend-plain-java-minimal`, `hamcrest-matcher-generator-endtoend-java-records` and `hamcrest-matcher-generator-endtoend-assertj`, which compile with `-Xlint:all,-processing -Werror`: javac's processing lint flags the test sources' own annotations (JUnit, JetBrains) that no processor claims, not generated code, and their poms say so; the other end-to-end modules (`plain-kotlin`, `mixed-kotlin-java`, `lombok`, `5x-compatibility-runner`) inherit `-Xlint:all -Werror` from the aggregator; the root `dev` profile adds that group unless `-DskipEndtoend` is set. The Maven example modules are `example-maven-java-hamcrest`, `example-maven-java-assertj` and `example-maven-kotlin`.

- They are documentation examples: parent `matcher-generator-parent`, in the root `<modules>` unconditionally, `maven.deploy.skip`, listed in the release `excludeArtifact` list.
- Their tagged regions feed the docs and README.
- Like the end-to-end exceptions named above, they compile with `-Xlint:all,-processing -Werror`.
- Their configuration sits in the test sources and the generator and the libraries have the test scope, so the production jar holds neither the generated code nor the configuration; `example-maven-kotlin` runs the processors through the `test-kapt` execution with explicit `<sourceDirs>` (see `docs/agents/kapt.md`).

`example-gradle-java` is the Gradle example, outside the reactor.
- It has its own wrapper, with `distributionSha256Sum` pinned; Renovate updates the wrapper.
- The CI job `example-gradle` builds it after `mvn install`.
- It resolves the project's own artifacts from `mavenLocal()` only, so a missing install fails the build.
- release-please bumps its version through `release-please-config.json` (`extra-files`, marker `x-release-please-version`).
- Do not add `META-INF/gradle/incremental.annotation.processors` for the processor: on Gradle 9.8.2 an `aggregating` or `isolating` line still forces a full recompilation, because Gradle's incremental processors may read only annotations of CLASS or RUNTIME retention and the processor claims `@javax.annotation.processing.Generated`, which has source retention (`isolating` also fails because each generated Java file has two originating elements). Declaring it needs an owner decision on the claimed annotations and on the retention of `@GenerateMatchers` (#363).

A new module pom needs its own xml entry in `extra-files` of `release-please-config.json` (own and parent version are raised together); dependencies on project artifacts use `${project.version}`. `scripts/ci/check-project-version.py` fails otherwise. The release type is `simple`: `maven` would rewrite the frozen 5.x suite's `@project.version@`.
