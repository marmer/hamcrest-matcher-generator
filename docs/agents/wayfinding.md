# Wayfinding process rules

Process rules for wayfinder maps and their tickets, used by `/wayfinder`. A map's Notes hold the project's decisions; this file holds how to work the map. Read **Every session** and **Merging**, plus the section for the ticket type you work on.

## Every session

- **Status view**: the `## Status` section is generated by `scripts/agents/issue-status.py <map>`; pass `--map <map>` to `issue.py claim`/`close`/`block` so they refresh it (`child` always does; see `docs/agents/issue-tracker.md`). The same applies to the spec and its tickets later.
- **Final report**: end the session's report with the owner's "Your to-dos" list and then the `/retro` request, as `docs/agents/implementation.md` ("Owner to-do list in the final report") describes.
- **One outward action per call**: run each push, PR creation, auto-merge and issue write as its own tool call, so a permission denial blocks only that action instead of the whole batch.

## Merging

- **Owner rule**: PRs created in wayfinder sessions are merged through GitHub auto-merge: right after opening the PR, the session enables auto-merge with the squash method (`enable_pr_auto_merge`), and GitHub merges once the required checks of the `main` ruleset pass (`Build`, `Verify JDK 17`, `Verify JDK 21`, `Verify JDK 25`, `Verify JDK latest`, `Domain docs in sync`; squash only, open review threads block). Never merge directly with `gh api -X PUT .../pulls/<n>/merge`. A red PR waits for the owner: fix it in the session if the failure is the PR's, otherwise report it; only the owner (repository admin, ruleset bypass) merges red. When the owner asks for a PR ("`/pr`", "PR und merge"), the session ends with auto-merge enabled on it. When the owner changes the ruleset while a PR is already green, auto-merge may not fire on its own: check the PR after the change and ask the owner to click "Squash and merge" if it stays open. Vendored skills (`.agents/skills/`, `skills-lock.json`) are never modified. After a squash merge, merge the base into the session branch before new work (`git fetch origin main && git merge --no-edit origin/main && git push`): the merge is conflict-free because the squash commit holds the same changes, needs no force-push (auto mode blocks reset + force-push), and the next PR shows only its own diff.
- **Clean branch**: every session leaves its branch with no commits outside a merged PR. At session start, check `git diff --stat origin/main HEAD` (content, not commit count: merged-in squash history leaves commits with an empty diff); fold any leftover change into a PR of its own, or name it explicitly in the PR that carries it.

## Grilling tickets

- **Skills**: grilling tickets use `grilling` + `domain-modeling`. Keep `GLOSSARY.md`/`docs/adr/` in sync with arc42 (`docs/agents/domain.md`).
- **Completion**: a round in which the owner accepts every answer and no question is left open counts as the confirmation of shared understanding; record the resolution without an extra confirmation round.
- **Helper prototypes**: a feasibility check run while grilling (by you or a subagent) that a decision rests on is re-run once from a clean copy and pushed as an unmerged `prototype/<name>` branch with a README of its gotchas, and linked from the resolution comment. The scratchpad dies with the container. Example: `prototype/structurizr-rendering`.
- **Helper research**: fact-finding a subagent does while grilling that a decision rests on is saved like a research ticket's findings: an unmerged `research/<name>` branch with the report under `docs/research/` (sources and unconfirmed points included), linked from the resolution comment. Examples: `research/sonarqube-cloud-token`, `research/pit-mutation-testing`.

## Prototype tickets

- **Shown to the owner**: before asking for a verdict, publish an overview page as an Artifact (each candidate's code plus its real output) and link it; the owner often reviews on a phone and cannot browse branches there. For API shape, build it with `scripts/agents/prototype-page.py` from the run output. For UI (pages, sites, layouts), publish a multi-file Artifact instead: each variant's rendered pages, Playwright screenshots at desktop and phone width, and an overview page linking into every variant. Example: branch `prototype/pages-site`.
- **On API shape** (the vendored `prototype` skill has only LOGIC and UI branches): hand-write the code the generator would emit, add a property "later", compile and run each candidate against the real libraries (classpath: `scripts/agents/prototype-classpath.sh`), and show the real javac/Hamcrest/AssertJ output. Cover the full **sample set** in the first round: flat POJO, nested POJO, record, null nested value, list, set and map of a generated type, all without `toString`. Keep the worktree at `/home/user/prototypes/<name>` (the scratchpad path changes on session restart). Examples: branches `prototype/completeness-check`, `prototype/mismatch-message-format`.

## Research tickets

- **Resolution**: the research subagent does the research itself; the `research` skill's step of starting a background agent is already done by its dispatch. It writes the report to `docs/research/<name>.md` in a worktree on a new `research/<name>` branch from `origin/main`, commits, pushes and opens no PR; then `issue.py comment <n>` with the gist and a link to the report on that branch, `issue.py close <n> --map <map>`, and `issue.py decide <map> <n> --gist "..."`, each as its own call. Dispatch it with the ticket number and the map's context; the steps live here.
- **Findings**: each closed research ticket's resolution comment gists the findings; full sources live on the unmerged `research/<name>` branches under `docs/research/` (e.g. `git fetch origin 'refs/heads/research/*:refs/remotes/origin/research/*'`).
