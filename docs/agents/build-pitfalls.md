# Build pitfalls

Facts the build environment hides. `scripts/agents/verify.sh` runs the checks in the right order (Spotless apply, full-reactor `install`, `verify` on JDK 21 and 17, domain-docs check; `--fresh` adds `fresh-repo`); use it for every full verification. The pitfalls below matter for ad-hoc runs (`-pl`, filtered tests), pom and CI changes, and failures.

- **Stale local `main` at session start**: the SessionStart hook (`.claude/hooks/session-start.sh`, configured in `.claude/settings.json`) runs in every session and fetches `origin` and fast-forwards `main` to `origin/main` through `scripts/agents/fast-forward-main.sh`, but only when `main` is checked out, the working tree is clean and the merge is a fast-forward; otherwise it leaves everything untouched and prints one line saying why. Cloud sessions also unshallow a shallow clone, pre-fetch Maven dependencies and install the pinned JDKs.
- **compile-testing on Java 17** requires `--add-opens=jdk.compiler/com.sun.tools.javac.*=ALL-UNNAMED` in Failsafe `<argLine>` — configured once in the root pom's `pluginManagement` for `maven-failsafe-plugin` (next to the `module.jar` property), so no module repeats it.
- **Unresolvable names fail the build for `@GenerateMatchers`**: one error per name. The deprecated `@MatcherConfiguration` only warns, as in 5.x, so keep configured names in `@GenerateMatchers` resolvable. Set `-Amatchergenerator.verbose` to see one note per skipped property with its reason.
- **`docs` module needs JDK 21+**: it is only built when the root profile `docs` (`<jdk>[21,)</jdk>`) is active, so a JDK 17 build skips it silently.
- **`maven-compiler-plugin` before 3.12 does not follow a relocation in `annotationProcessorPaths`** (fails with "Missing: ...annotationprocessor:jar"): that is why the 5.x artifacts are bridge jars, not relocation POMs (ADR 0002). Do not turn them back into pom-only relocations. The root pom's `maven-compiler-plugin.version` stays below 3.12 (newer versions break the Kotlin end-to-end modules, see #110) and the 5.x consumer build uses it too.
- **JUnit Platform version mismatch**: Surefire 3.5.2 needs `junit-platform-launcher` explicitly on the classpath, at the Platform version that matches Jupiter. The root pom manages both through `junit.version`, which moves with Jupiter; never pin the launcher separately.
- **Older `junit-platform-commons` from Jazzer**: `jazzer-junit` declares `junit-platform-commons` 1.9.0, which wins over the 6.x line and kills the surefire fork with `NoSuchMethodError CollectionUtils.forEachInReverseOrder`. The root pom pins it to `${junit.version}` (comment above the `junit-platform-commons` entry in `dependencyManagement`, #290). Never remove that pin or pin Platform artifacts to literal versions; a new test-scope dependency that brings an older JUnit artifact needs the same managed pin.
- **JDK 25 implicit annotation processing disabled**: `@AutoService` was removed from `MatcherGenerationProcessor.java`; a manual `META-INF/services/javax.annotation.processing.Processor` resource is used instead. The `endtoend-plain-java-minimal` module uses `<annotationProcessorPaths>` to declare the AP explicitly.
- **Lombok on newer JDKs**: each JDK needs a Lombok release that supports it (JDK 25 ≥ 1.18.44, JDK 27 ≥ 1.18.48); an unsupported JDK fails in javac with `ExceptionInInitializerError: com.sun.tools.javac.tree.EndPosTable`.
- **Agent edits to `.claude/settings*.json` are blocked** in auto mode (Self-Modification): give the owner the exact snippet to add instead of loading `update-config`.
- **Error Prone and NullAway (JDK 21+ profile `static-analysis`)**: javac needs the `--add-exports` from `.mvn/jvm.config` in the Maven JVM (Error Prone calls javac internals, JEP 396). The file is harmless on JDK 17: it exports packages that exist there too, and nothing on that leg uses them, so keep it on every JDK. The `mvn` launcher reads it into `MAVEN_OPTS`, and `./mvnw` runs that launcher, so both pick it up. The rest: `-XDshould-stop.ifError=FLOW` and the Error Prone flags inside one `-Xplugin:ErrorProne ...` argument. When the plugin fails to start, javac reports the check flags as `invalid flag: -Xep:...`, which hides the real error. A module that declares its own `annotationProcessorPaths` must use `combine.children="append"`, or the profile's Error Prone and NullAway paths are dropped.
- **Spotless runs in the `install` lifecycle** and fails on new, unformatted code; `verify.sh` applies it first. For ad-hoc runs: `./mvnw -o com.diffplug.spotless:spotless-maven-plugin:<spotless.version from the root pom>:apply` (the `spotless:apply` prefix does not resolve offline).
- **JaCoCo branch floor 0.99** merges the unit and IT exec files per module: a filtered run (`-Dit.test=...`) fails the check or leaves a stale exec. Use `clean`; `-Djacoco.skip=true` for intermediate installs; with `-am` filters add `-Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`.
- **Failsafe 3.6 ignores `-DskipTests`**: it runs the integration tests anyway (3.5.2 skipped them), so every `-DskipTests` build also passes `-DskipITs`, or the JaCoCo check fails on the IT-only coverage.
- **End-to-end fixtures live outside the configured model package**: package configuration scans the test classes there too and generates assertions for them.
- **google-java-format 1.37.0** fails inside Spotless with an `InvocationTargetException` on Javadoc-carrying files, and Spotless hides the cause. The root pom pins 1.36.0 until that is fixed.
- **Shared `~/.m2` serves stale sibling artifacts**: `-pl` without `-am` resolves sibling modules from `~/.m2`, so a build can pass against an old sibling; build the full reactor (`install -DskipTests -DskipITs`) first. This covers core, the backends and the generator jar that end-to-end modules run: after a generator change, `install -pl <backend> -am -DskipTests -DskipITs`, then `clean verify` the end-to-end module, because incremental compilation can skip regenerating its sources and stay green on stale classes.
- **A green local `verify` can hide missing installs**: the shared `~/.m2` holds the artifacts of earlier `install` runs, while CI runs a plain `verify` on a fresh runner, so maven-invoker consumer builds (`hamcrest-matcher-generator-endtoend-plain-kotlin`) and other project-artifact lookups can pass locally and fail there. After changing poms, invoker consumer builds or end-to-end modules run `scripts/agents/verify.sh --only fresh-repo`.
- **Cloud sessions cannot list repository secrets or settings** (the proxy answers 403 for `gh api repos/marmer/hamcrest-matcher-generator/actions/secrets`). The required checks: `gh api repos/marmer/hamcrest-matcher-generator/rules/branches/main --jq '.[]|select(.type=="required_status_checks")'`. Whether a secret is set shows as a masked `env:` entry in the job log; whether it is accepted shows in a failing validation step.
- **Maven Central HTTP 429** (rate limit, frequent with parallel subagents sharing `~/.m2`): Maven may store the 429 error text as a `.pom` or `.jar` in `~/.m2/repository`, failing later builds ("Non-parseable POM", `NoClassDefFoundError`). Delete that version directory and rebuild offline with `-o`; the SessionStart hook pre-fetches dependencies for that and logs to /tmp/session-start.log; if ~/.m2 is empty, read that log first. Each failed attempt there names its cause from Maven's output.
- **Windows with a jabba-managed JDK** (owner's machine only): `JAVA_HOME="/c/Users/MarianoMertinat/.jabba/jdk/corretto@17" PATH="$JAVA_HOME/bin:$PATH" ./mvnw clean install`.
- **Parallel reactor**: `.mvn/maven.config` sets `-T 1C`, so builds run modules side by side; a command-line `-T` replaces it (`-T 1` serial, `-T 2` two threads). The release build, the release dry run, CI's mutation job and CI's Sonar job pin `-T 1`. When a build fails only in parallel, rerun it with `-T 1`: a failure that stays is real, one that goes away is an ordering or shared-state problem. The thread-safety warnings name `org.jetbrains.kotlin:kotlin-maven-plugin:2.1.20` (`example-maven-kotlin`, `hamcrest-matcher-generator-endtoend-mixed-kotlin-java`, `hamcrest-matcher-generator-endtoend-plain-kotlin`). On 4 cores `clean verify` got about 23 % faster on JDK 21 and about 13 % on JDK 17; the mutation build about 7 % (one run each), so it stays serial. A parallel `install` writes to the `~/.m2` that sibling worktrees share, just as a serial one does, so run it alone (`docs/agents/implementer-brief.md` step 4).
- **No hand-over through a JVM system property**: a build step must not hand a value to a later step through a JVM-wide system property, because surefire and failsafe restore a snapshot of the Maven JVM's system properties after each fork, so in the parallel reactor a property set during the build can vanish (#382: `Could not load Structurizr` in the docs build). The render names the Structurizr home in the JRuby `ENV` from `docs/src/docs/extensions/structurizr_home.rb`, which is required before asciidoctor-diagram.
- **PIT history makes the mutation build incremental**: `target/pit-history` in the repository root is read and written by `-Pmutation`. A second run in the same checkout analyses only the changed mutants (1 to 2 units per module instead of 3 to 16). Delete that directory before timing a mutation run.
- **Mutation build offline**: `./mvnw -o verify -Pmutation` fails with "in offline mode" until PIT's runtime plugins are in `~/.m2`. Fetch them once online: `./mvnw org.pitest:pitest-maven:1.30.2:help`, then `./mvnw org.apache.maven.plugins:maven-dependency-plugin:3.8.1:get -Dartifact=org.pitest:pitest-junit5-plugin:1.2.3` and the same with `-Dartifact=org.pitest:pitest-history-plugin:0.0.1`.
- **Squash merges and reformat commits**: after a squash merge, a follow-up commit adds the squash sha to `.git-blame-ignore-revs`; a reformat commit holds only `spotless:apply` output, with any config change in an earlier commit.
